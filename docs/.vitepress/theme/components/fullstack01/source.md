# 一、适合你的学习路线

## 1. 技术主线怎么选？

**React / TypeScript → Spring Boot 模块化单体 → PostgreSQL。**

选择这条路线，是为了沿用你已有的 Spring Boot 背景，把主要精力花在业务设计、数据库和工程交付上。

这里的“模块化单体”，可以先理解为：**代码按成员、项目、工单等业务划分模块，整体作为一个后端应用运行。**

Node 同样可以承担核心后端。本系列会在后半程引入 Node BFF，并安排与 Java 实现的对照，帮助你掌握能够跨语言迁移的能力。

| 位置 | 本系列选择 | 学习重点 |
|---|---|---|
| 前端 | React + TypeScript，沿用熟悉的构建方式 | 服务端状态、错误恢复、权限交互、并发冲突提示 |
| 核心后端 | Java 21 + Spring Boot 4.1.x | 用例组织、授权、事务、业务规则、可测试性 |
| 数据库 | PostgreSQL 18 | SQL、关系建模、约束、索引、事务与迁移 |
| BFF / 工具服务 | Node.js 24 LTS；需要结构化框架时使用 NestJS | 页面聚合、会话适配、超时与失败处理 |
| 运行环境 | Docker Compose + 反向代理 + CI/CD | 配置、发布、日志、备份、恢复 |
| 后续组件 | Redis、后台任务、对象存储 | 在具体需求出现时学习缓存和异步处理 |

本次核对的 Spring Boot 官方文档列出 4.1.1，支持 Java 21；Node 官方发布表将 24 标为 LTS。这里先确定教学基线，实际工程会锁定具体依赖版本。[[spring]] [[node]]

### BFF 什么时候加入？

当一个页面需要聚合多个服务、管理浏览器会话，或者不同终端需要不同接口形态时，BFF 就有明确的用途。它可以承载面向使用体验的编排逻辑；新增一层也会增加网络跳转和运行维护成本。[[bff]]

因此，项目初期保持一个核心业务服务和一个数据库。后续通过实际需求判断是否增加组件，练习“为什么要加”的决策能力。

## 2. 优先核查的六项能力

你的现有背景已经覆盖了相当一部分开发工作。下面这些是本系列优先核查和补强的地方，**并不预设你完全不会**。

| 能力 | 自测问题 | 能力证据 |
|---|---|---|
| 业务建模 | 需求只有一句话时，能否列清实体、关系、权限和状态规则？ | 数据模型、规则清单、接口契约 |
| 数据正确性 | 两个请求同时修改或创建时，结果是否仍符合规则？ | 唯一约束、事务、并发用例 |
| 资源授权 | 已登录用户修改 URL 中的 ID，能否访问别人的数据？ | 越权测试和租户隔离规则 |
| 故障处理 | 超时发生后，如何判断业务到底成功没有？ | 幂等策略、错误契约、追踪日志 |
| 性能分析 | 接口慢时，能否区分 SQL、网络、连接池和外部服务？ | 执行计划、指标和定位记录 |
| 运行交付 | 能否发布、升级数据库、恢复备份并定位生产问题？ | 部署说明、恢复演练和运行手册 |

例如，你如果已经熟悉统一登录，认证章节可以快速通过；但仍要检查：**“登录以后，能操作哪个组织的哪个资源”是否也有完整保证。**

# 二、贯穿项目：TeamFlow 团队工单平台

我们用一个接近管理平台日常工作的项目贯穿全系列：

> **一个用户可以加入多个团队；团队拥有项目；成员在项目中创建、指派、处理工单。**

第一阶段只做项目列表、创建工单、工单查询和状态修改。之后逐步加入组织角色、租户隔离、并发控制、导入导出、通知、审计和运行监控。

这里的“租户”就是一个相互隔离的团队或公司。甲团队的用户不能因为知道乙团队的工单 ID，就看到或修改乙团队的数据。

| 阶段成果 | 你要能展示什么 |
|---|---|
| 功能闭环 | 页面提交后写入真实数据库，刷新仍能查询 |
| 正确性闭环 | 非法状态、重复业务编号和并发修改都有明确结果 |
| 安全闭环 | 直接调用 API 也不能越权，列表、详情和文件权限一致 |
| 运行闭环 | 能发布、追踪故障、执行数据库升级并恢复备份 |

这也是后续整理全栈项目经历时的证据来源：**说明自己解决了什么问题、怎么验证，而不只是列出使用过的框架。**

# 第 01 篇：从“把接口接通”到“对业务结果负责”

**本篇目标：**看懂一次“创建工单”背后的完整职责，能够说明数据为什么正确、权限在哪里执行、失败后保留什么结果，以及如何验证。

本篇是设计与边界课。HTTP 和 SQL 用于说明具体契约；Java 代码是明确省略基础设施实现的结构示意。**第 02 篇会把第一条业务链路做成可运行工程。**

## 1. 先改变“做完了”的判断标准

收到需求：

> 给项目加一个创建工单功能。

你很熟悉页面部分：表单、输入校验、提交状态、接口调用、成功提示、刷新列表。已有 BFF 经验，也会考虑接口聚合、登录态和错误处理。

全栈需要继续把问题问到底：

1. **谁可以在这个项目里创建工单？**
2. 用户把项目 ID 改成别的团队的，会怎样？
3. 两个请求同时创建相同业务编号，会怎样？
4. 工单写入成功，审计写入失败，保留哪个结果？
5. 数据库提交成功，但响应在网络里丢了，客户端该怎样重试？
6. 上线后用户说“点了没反应”，你靠什么定位？

**你负责的范围，从一次调用扩展到这个业务承诺在正常、异常和并发情况下都成立。**

这并不要求你一次掌握所有运维和架构知识。学习时按一个小功能逐步补齐这些保证，更容易形成可以迁移到其他项目的能力。

## 2. 先写业务规则，再写接口

本课采用一套明确的教学规则：

- 一个用户可以属于多个租户。
- 项目继承租户角色：`ADMIN`、`MEMBER` 可以创建工单，`VIEWER` 只读。
- 本课还没有“私有项目成员”这层权限；后续如果加入，必须扩展授权判断。
- 工单标题需要经过服务端规范化和非空校验；具体长度口径在 API 契约章统一。
- 每个工单属于一个项目，且工单与项目必须属于同一个租户。
- 为了练习业务唯一性，本课允许提交业务编号：长度为 1—32 个字符，首字符为大写字母或数字，其余字符允许大写字母、数字和连字符，例如 `BUG-101`；同一项目内不可重复。
- 创建工单必须同时写入一条审计记录。
- 通知是后续能力；当前创建用例不直接调用邮件服务。

业务规则确定后，请求可以写成：

```http
POST /api/tenants/{tenantId}/projects/{projectId}/tickets
Content-Type: application/json
```

```json
{
  "ticketKey": "BUG-101",
  "title": "修复登录后的跳转问题"
}
```

创建并提交成功后返回：

```http
HTTP/1.1 201 Created
Location: /api/tenants/{tenantId}/projects/{projectId}/tickets/{id}
```

```json
{
  "id": "服务端生成的工单 UUID",
  "ticketKey": "BUG-101",
  "title": "修复登录后的跳转问题",
  "status": "OPEN"
}
```

这里有两个不同的标识：

- `id` 是技术主键。
- `ticketKey` 是业务编号。

二者唯一的目的不同，也都不能自动代表“一次请求”。

请求体不让客户端决定创建人。服务端从经过验证的身份上下文取得 `userId`。URL 中的 `tenantId`、`projectId` 表示用户想操作的目标，仍然需要服务端验证。

**认证回答“你是谁”，授权回答“你能对这个资源做什么”。** 有效登录并不代表对所有租户和项目都有权限。OWASP 建议默认拒绝，并在每次请求中执行权限检查。[[auth]]

## 3. 把一条请求拆成明确职责

| 位置 | 本例中的职责 |
|---|---|
| React 页面 | 收集输入、提供即时校验、展示请求状态和可理解的错误 |
| 认证组件 | 验证凭据，构造可信的当前用户身份 |
| Controller | 接收 HTTP 参数，执行请求格式校验，调用业务用例，映射响应 |
| Service / 用例层 | 判断成员角色、核实项目归属、执行创建规则、组织事务 |
| Repository | 执行带租户作用域的查询与写入 |
| PostgreSQL | 保存数据，通过约束保障可表达的数据不变量 |
| 运行观测 | 记录请求关联信息、异常和耗时，支撑问题定位 |

例如，“标题不能为空”同时出现在前端和服务端是合理的：

- 前端帮助用户及时修改。
- 服务端处理所有进入系统的请求。
- 数据库也可以对关键字段设置非空和格式约束。

这些校验服务于不同的边界。浏览器中的代码由客户端控制，服务端不能依据“页面已经校验过”就跳过自己的检查。

### 互动：改变场景，观察责任位置

下面是请求流程模拟，不连接真实服务。切换不同场景，观察关键处理位置。

[[boundary-interactive]]

如果以后加入 Node BFF，它可以做概览聚合、响应整形和会话适配。核心业务服务仍要有明确的数据所有权与授权保证，避免另一条调用路径绕过关键规则。

## 4. 工程案例：一个创建用例怎样组织？

下面是 Service 的结构示意。`Actor`、仓储接口、DTO 和异常类型都需要在工程中实现；仅复制这个方法不能构成完整应用。

```java
@Transactional
public TicketView createTicket(
        Actor actor,
        UUID tenantId,
        UUID projectId,
        CreateTicketCommand command) {

    // actor 来自验证后的身份；目标租户仍需授权。
    accessPolicy.requireTicketCreation(
        actor.userId(), tenantId);

    // 查询本身带 tenantId，确保项目属于目标租户。
    projectRepository.findByTenantAndId(tenantId, projectId)
        .orElseThrow(ResourceNotFoundException::new);

    var ticket = Ticket.open(
        UUID.randomUUID(),
        tenantId,
        projectId,
        command.ticketKey(),
        command.title(),
        actor.userId()
    );

    ticketRepository.insert(ticket);
    auditRepository.recordCreated(ticket, actor.userId());

    return TicketView.from(ticket);
}
```

这段代码的价值在于能看见五个决定。

### ① 当前用户与请求数据分开

`Actor` 不能由 JSON 反序列化后直接当成可信身份。

客户端可以提交“我想创建什么”，但不能通过修改请求体来决定“我是谁”。

### ② 权限有明确策略

`requireTicketCreation` 检查当前有效租户成员关系和 `ADMIN / MEMBER` 角色。

这里采用的是前面约定的权限模型：项目继承租户角色。如果以后有私有项目，还要补充项目级权限。

### ③ 查询带业务作用域

查询条件同时包含租户与项目 ID。

也就是说，我们查询的是：

> 这个租户里的这个项目。

### ④ 业务对象维护自身规则

`Ticket.open` 在本示例中负责：

- 标题规范化。
- 编号格式检查。
- 初始状态设为 `OPEN`。

这样创建规则有明确归属，其他调用入口也可以复用。

### ⑤ 相关写入共同提交

工单和审计使用同一数据库、同一事务管理器和同一事务。

但 `@Transactional` 生效有条件。在默认代理模式下，事务方法需要通过代理调用。同一个对象内自调用带注解的方法，不会因此新建该方法声明的事务；如果外层已有事务，内层仍可能在外层事务中执行。[[tx-proxy]]

默认回滚规则主要针对运行时异常和 `Error`；异常被吞掉或回滚规则被改变时，结果也会变化。[[tx-rollback]]

因此，本例假设：

- 这是经 Spring 代理调用的 Service 方法。
- 仓储参与同一事务。
- 写入失败的异常没有被吞掉。

实际工程要用“让审计写入失败”的测试验证回滚，不能只看到注解就认定正确。

**换成 NestJS，核心问题仍然一样：谁发起操作、是否有权限、哪些规则必须成立、哪些写入需要共同提交。** 变化的是依赖注入、事务 API 和数据库访问方式。

## 5. 数据库约束：把规则落到数据上

为了聚焦本课，下面给出三张表的 DDL：项目、工单和审计。

完整的用户、租户和成员表会在数据建模章节加入；**这三张表本身不实现登录和授权**。

```sql
CREATE TABLE project (
    tenant_id uuid NOT NULL,
    id uuid NOT NULL,
    name text NOT NULL,
    PRIMARY KEY (tenant_id, id)
);

CREATE TABLE ticket (
    tenant_id uuid NOT NULL,
    id uuid NOT NULL,
    project_id uuid NOT NULL,
    ticket_key text NOT NULL,
    title text NOT NULL,
    status text NOT NULL DEFAULT 'OPEN',
    created_by uuid NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),

    PRIMARY KEY (tenant_id, id),
    CONSTRAINT uq_ticket_key
        UNIQUE (tenant_id, project_id, ticket_key),
    CONSTRAINT fk_ticket_project
        FOREIGN KEY (tenant_id, project_id)
        REFERENCES project (tenant_id, id),
    CONSTRAINT ck_ticket_key
        CHECK (ticket_key ~ '^[A-Z0-9][A-Z0-9-]{0,31}$'),
    CONSTRAINT ck_ticket_title
        CHECK (length(btrim(title)) > 0),
    CONSTRAINT ck_ticket_status
        CHECK (status IN ('OPEN', 'IN_PROGRESS', 'DONE'))
);

CREATE TABLE ticket_audit (
    tenant_id uuid NOT NULL,
    id uuid NOT NULL,
    ticket_id uuid NOT NULL,
    actor_user_id uuid NOT NULL,
    event_type text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),

    PRIMARY KEY (tenant_id, id),
    FOREIGN KEY (tenant_id, ticket_id)
        REFERENCES ticket (tenant_id, id)
);
```

理解三个重点即可：

- `UNIQUE` 限制业务编号重复。
- 复合外键限制同租户引用。
- `CHECK` 限制字段值。

PostgreSQL 支持这些约束；它们让不符合约束的写入失败。[[constraints]]

这个模型还刻意保留了几个边界：

1. **复合外键不会自动给 SELECT 添加租户过滤。** 它保证工单引用同一租户内存在的项目。
2. 状态 `CHECK` 只限制可存的值；例如 `DONE` 能否回到 `OPEN`，需要状态转换规则。
3. `btrim` 的示例只去除首尾普通空格；完整的空白处理和长度口径要由 API 契约、服务端规范化和数据库设计共同确定。
4. 创建人和操作者在这份局部模型中只是 UUID 字段；完整身份关系将在第 04 篇建立。

### 为什么“先查再插入”仍然会重复？

假设应用这样处理：

> 先查询 `BUG-101` 是否存在，不存在就插入。

考虑下面的时序：

| 时刻 | 请求 A | 请求 B |
|---|---|---|
| 1 | 查询：不存在 | |
| 2 | | 查询：不存在 |
| 3 | 执行插入 | |
| 4 | | 执行插入 |

两个请求都通过了“先查”这一步。

**在本例中，最终保障编号唯一的是数据库唯一约束。** 预查询可以改善错误提示，但不能替代约束。

加上普通事务也不等于把全部请求排成单线程。以 PostgreSQL 默认的 Read Committed 为例，普通 SELECT 读取语句开始时的已提交快照，不能据此断言之后没有竞争写入。[[isolation]]

发生编号唯一冲突时，工程应识别具体的 `uq_ticket_key` 约束，再映射为业务冲突；连接失败等数据库异常不能全部包装成“编号已存在”。

本课采用让异常穿出事务方法、完成回滚后再映射错误的处理方式，避免留在失败事务中继续查询。

## 6. 业务唯一性和请求幂等，要分开设计

这两个概念很容易在“重复提交”里混到一起。

| 问题 | 本质 | 本项目的例子 |
|---|---|---|
| **业务唯一性** | 哪些数据在业务上不允许同时存在？ | 同一项目不能有两个 `BUG-101` |
| **请求幂等** | 同一次操作执行多次，怎样避免产生额外业务效果？ | 第一次创建已成功，但客户端超时后再次提交 |

假如每次 POST 都生成一个新 UUID，再给它分配不同业务编号，数据库中的主键和编号都没有冲突，却可能产生两张用户本意相同的工单。

后续会设计请求幂等键：

1. 客户端对同一次操作保留一个键。
2. 服务端把键、调用者与租户作用域、请求内容指纹、执行状态和结果按约定持久化。
3. 同一键重试，返回同一次操作的结果。
4. 同一键搭配不同请求内容，应拒绝。

本篇尚未实现这套机制。

当前相同业务编号的第二次创建返回冲突，是业务唯一性的结果，不能据此宣称接口已经完整支持请求幂等。

## 7. 本地事务能覆盖到哪里？

本例的业务承诺是：

> **工单记录和审计记录共同提交；其中任一写入失败且满足回滚条件，就共同回滚。**

但数据库事务无法把外部邮件服务、任意 HTTP 请求一起变成本地原子操作。两种顺序都有问题：

- **先发邮件，再提交数据库：**邮件已经发出，但数据库可能提交失败。
- **先提交数据库，再发邮件：**数据库已经成功，但进程可能在发送前退出。

需要可靠通知时，可以在同一数据库事务中写入：

- 工单。
- 审计。
- 一条待发送事件，即 **Outbox**。

后台任务读取已提交事件、发送通知、失败后重试，同时处理重复投递。该模式解决业务写入与事件保存之间的双写问题。[[outbox]]

这里的“可靠”有明确范围：**待发送意图不会仅存在于内存中。** 实际送达仍取决于发送端、接收端和重试策略，不能简单承诺邮件绝不会重复或永远不会失败。

另外：

> **客户端超时只说明客户端没及时拿到结果，不能单独证明数据库没有提交。**

这正是第 08 篇要加入结果查询和重试幂等的原因。

## 8. 错误响应也是接口契约的一部分

本系列先采用如下约定：

| 情况 | 响应约定 |
|---|---|
| 成功创建并提交 | `201`，返回新资源和 `Location` |
| 参数格式或输入规则不满足 | `400`；本系列统一使用这一约定 |
| 凭据缺失、失效或无效 | `401`，由认证层提供适用的 `WWW-Authenticate` |
| 身份有效，但角色不允许创建 | `403` |
| 项目不存在，或按既定策略隐藏无权访问资源 | `404` |
| 业务编号冲突 | `409`，返回稳定的业务错误码 |
| 未预期的内部故障 | 合适的 `5xx`，客户端拿到可追踪标识 |

`400` 与 `422` 可以采用不同的 API 约定；这里选择 `400` 并保持一致。RFC 9110 定义了这些 HTTP 状态的语义，也允许用 `404` 隐藏不愿披露的资源存在性。[[http]]

编号冲突时，可以返回：

```json
{
  "code": "TICKET_KEY_CONFLICT",
  "message": "当前项目内已存在这个工单编号",
  "traceId": "一次请求的追踪标识"
}
```

这三个字段各有用途：

- 前端根据稳定的 `code` 决定行为。
- `message` 提供用户能理解的说明，可以做多语言。
- `traceId` 用于关联日志。

这样，前端就不需要依赖“错误提示必须包含某几个中文字符”来判断业务情况。

统一错误结构的同时，也应保留有意义的 HTTP 状态，让调用方可靠地区分登录问题、权限问题、输入问题、业务冲突和服务故障。

## 9. 课后工程练习：定义“创建工单完成了”

先不增加页面功能，给当前用例写一张验收清单。

| 验证场景 | 预期结果 |
|---|---|
| MEMBER 在所属租户的项目中创建合法工单 | `201`；有一条工单和一条创建审计 |
| VIEWER 直接调用创建 API | `403`；工单和审计都不增加 |
| 修改 tenantId / projectId，访问其他租户资源 | 按既定 `403/404` 策略拒绝；不泄露数据、不产生写入 |
| 绕过前端提交空标题 | `400`；不产生写入 |
| 同一项目并发创建同一业务编号 | 至多一条工单成功提交；冲突得到可识别结果 |
| 模拟审计写入失败 | 工单写入回滚；没有“工单成功但缺审计”的结果 |
| 创建成功后刷新页面 | 能从数据库重新查到该工单 |
| 响应在提交后丢失 | 能说明结果不确定；第 08 篇完善查询与幂等重试 |

### 本次作业包含三个产物

1. 写出创建工单的请求、成功响应、失败响应。
2. 标出至少五条业务规则由前端、服务端和数据库中的哪些位置保障。
3. 为上表前六种情况写出 `Given / When / Then` 验收描述。

例如：

```text
Given：用户在租户 A 中的角色是 VIEWER
When：直接向租户 A 的项目提交创建工单请求
Then：返回 403
And：ticket 与 ticket_audit 的记录数都不增加
```

可以使用 AI 辅助生成表结构、代码和用例，但审阅时要问具体问题：

- 这段查询是否带租户条件？
- 两个请求并发时，约束在哪里？
- 第二次写入失败，第一次写入是否真的回滚？

**能解释这些结果，才说明这部分能力被自己掌握了。**

## 10. 自测：6 道选择题

每题 1 分，共 6 分。文件中的题目支持选择答案、评分和查看解析；这里也保留完整题目与答案，方便直接阅读。

[[quiz-interactive]]

### 第 1 题：已登录用户改了租户 ID，服务端应怎样处理？

A. JWT 有效就执行。  
B. 校验目标租户成员关系、资源归属和目标动作权限。  
C. UUID 很难猜，可以省略检查。

**答案：B。**

有效身份只说明请求者是谁，仍要判断目标资源与动作是否获准。

### 第 2 题：两个请求都查到 BUG-101 不存在，谁最终保障编号唯一？

A. 前端禁用按钮。  
B. 查询之后立刻插入。  
C. 数据库中的对应唯一约束。

**答案：C。**

查询和写入之间存在竞争窗口，数据库约束才能约束同时到来的写入。

### 第 3 题：同一有效事务里，审计写入抛出未吞掉的运行时异常，会怎样？

A. 工单和审计写入共同回滚。  
B. 工单保留、审计丢失。  
C. 自动向用户发送补偿邮件。

**答案：A。**

题设已经限定同一事务、事务生效和符合默认回滚规则的异常传播。

### 第 4 题：复合外键 `(tenant_id, project_id)` 最直接保障什么？

A. SELECT 自动按租户过滤。  
B. 当前用户一定是管理员。  
C. 工单引用同一租户中存在的项目。

**答案：C。**

外键保障引用关系；读取范围和调用者授权仍然要单独实现。

### 第 5 题：工单已提交，但通知发送失败，后续应怎样提高可靠性？

A. 把浏览器超时设置得足够长。  
B. 同事务保存 Outbox 事件，后台发送、重试并处理重复投递。  
C. 认为数据库事务会撤销外部邮件。

**答案：B。**

持久化发送意图后，进程重启仍有机会继续执行；通知重复问题也需要处理。

### 第 6 题：每次重试都生成新 UUID 和新业务编号，为什么仍可能创建逻辑重复工单？

A. 数据库不能使用 UUID。  
B. 所有 POST 都必须禁止重试。  
C. 唯一技术标识没有识别“这是同一次业务操作”。

**答案：C。**

技术标识唯一、业务编号唯一和请求幂等，是三个需要分别定义的保证。
