React + Node.js 的第一条聊天链路｜第 14 / 40 篇｜第三阶段：工程开发｜阅读约 12–18 分钟

前十三篇，我们聊过模型、记忆、上下文、格式和幻觉。

现在，先把这些概念放到旁边。打开一个网页，输入“你好”，点一下按钮，让它真的回一句话。

今天不造一个完整的 ChatGPT。先让第一通电话接通。

一、这一篇，只接通三个角色

React 页面：收集问题，显示回答
        ↓ POST /api/chat
Node.js 后端：检查请求，保管密钥，调用模型
        ↓ HTTPS 请求
模型服务：生成回答
        ↓
Node.js 整理结果 → React 显示

这次先做单轮、非流式聊天：发一个问题，等一份完整结果。流式输出、多轮记忆和数据库后面再接。

页面可以保留几条聊天气泡，但本次请求只发送最新问题。界面看得见历史，不代表模型收到了历史。这也是本篇故意保留的边界，不是记忆功能失灵。

我们还准备了一个“模拟助手”：不用 API Key，只回显问题。它不聪明，但能帮你先确认线路有没有接错。

二、密钥放后端，不是给前端换个变量名

你可能很想直接在 React 中调用模型：少写一个服务，多省事。

问题是，浏览器里的密钥可能被取走，用你的额度发请求。模型服务的秘密 API Key 应由后端保管，不能直接放进浏览器，也不要提交到仓库。[1]

尤其别写：

VITE_OPENAI_API_KEY=你的真实密钥

Vite 默认会把带 VITE_ 前缀的环境变量暴露给客户端代码。把密钥搬到这样的环境变量里，并没有把它藏起来。[2]

本篇的浏览器只认识 /api/chat；模型名称和密钥由 Node.js 读取。

三、先把工程启动起来

配套工程已经准备好。下载并解压文末的工程包，进入其中的 project 目录，使用 Node.js 22.12 或更新版本。

主要文件分工如下：

project/
├── src/App.tsx          # React 输入框、气泡、等待和错误提示
├── server/app.ts        # POST /api/chat 路由与输入检查
├── server/model.ts      # 模拟回复或调用真实模型
├── server/provider.ts   # 识别完成、拒绝、截断等结果
├── server/http.ts       # 限制请求体大小、读取和返回 JSON
├── shared/protocol.ts   # 前后端约定及响应结构检查
├── vite.config.ts      # 开发时把 /api 转给 Node.js
└── .env.example        # 只有空白配置，没有真实密钥

在 终端 A 中执行：

npm install
cp .env.example .env
npm run server

Windows PowerShell 可以把复制命令换为 Copy-Item .env.example .env。

然后在同一个目录打开 终端 B：

npm run dev

浏览器打开 http://127.0.0.1:5173，输入“你好”。默认 MODE=mock，你应该看到：

【模拟回复，未调用模型】收到：你好

这一步成功，说明页面、请求、后端和返回展示接通了。还不能说明真实模型已经接入。

工程的后端直接使用 Node.js 内置 HTTP 与 Fetch，没有额外引入 Web 框架。运行脚本使用 TypeScript 类型剥离；它不是类型检查，所以仍要单独运行 npm run check。[3]

四、先约定返回什么，前端就不用猜

浏览器提交的内容只有一个字段：

{ "question": "解释一下闭包" }

后端返回类似这样的数据。下面的 ID 是示意值：

{
  "status": "answered",
  "text": "【模拟回复，未调用模型】收到：解释一下闭包",
  "requestId": "示例请求编号",
  "mode": "mock"
}

这里沿用第 12 篇的思路，但换成适合本次纯文本聊天的小契约：answered 表示可以显示回答；refused、incomplete、failed 分别表示拒绝、不完整和失败。text 承载对应文字，requestId 由后端生成，mode 区分模拟和真实调用。

我们暂时没接知识库，所以不加入 sourceIds，也不假装有“证据充分”的判断。answered 是本次链路的状态，不是事实认证。

工程中的路由还会检查 JSON、问题类型、空白输入和长度。2000 字符是本篇的输入限制，不是 Token 计数；完整上下文预算仍要使用第 11 篇的方法。

五、后端最核心的工作：拿到问题，返回结果

打开 server/model.ts。这个文件完整如下：

import { setTimeout as delay } from "node:timers/promises";
import { normalizeResponse } from "./provider.ts";
import type { Result } from "../shared/protocol.ts";

export async function answer(
  question: string,
  mode: "mock" | "live",
  signal: AbortSignal
): Promise<Result> {
  if (mode === "mock") {
    await delay(500, undefined, { signal });
    return { status: "answered", text: `【模拟回复，未调用模型】收到：${question}` };
  }
  const key = process.env.OPENAI_API_KEY;
  const model = process.env.OPENAI_MODEL;
  if (!key || !model) throw new Error("MISSING_MODEL_CONFIG");

  const response = await fetch("https://api.openai.com/v1/responses", {
    method: "POST",
    signal,
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${key}`
    },
    body: JSON.stringify({
      model,
      store: false,
      max_output_tokens: 1200,
      instructions: "你是中文技术学习助手。解释清楚，不编造接口；不确定就说明。",
      input: [{ role: "user", content: question }]
    })
  });
  if (!response.ok) throw new Error(`UPSTREAM_HTTP_${response.status}`);
  return normalizeResponse(await response.json());
}

上半段是模拟模式，故意等半秒再回显。下半段才调用真实模型。

instructions 由后端设置，浏览器不能提交一个 role: "system" 就改变应用的消息结构。这里调用的是 Responses API；input 装当前问题，返回后还需要检查生成状态和输出内容。[4]

工程里的 normalizeResponse 做四件事：识别拒绝，拦住不完整结果，确认生成已完成，再提取文本。它不会执行回答中的代码，也不会判断回答事实正确。

这里没有注册工具，没有读取你的公司文档，也没有自动联网搜索。接通模型，不代表它突然拥有你的业务资料。

六、React 不用变复杂：发送时锁住，结束后解锁

src/App.tsx 的完整代码如下。重点看三件事：提交问题、检查结果、更新界面。

import { useEffect, useRef, useState } from "react";
import type { FormEvent } from "react";
import { isReply } from "../shared/protocol";

type Message = { role: "user" | "assistant"; text: string };

export default function App() {
  const [question, setQuestion] = useState("");
  const [messages, setMessages] = useState<Message[]>([]);
  const [busy, setBusy] = useState(false);
  const [error, setError] = useState("");
  const controller = useRef<AbortController | null>(null);
  useEffect(() => () => controller.current?.abort(), []);

  async function send(event: FormEvent<HTMLFormElement>) {
    event.preventDefault();
    const text = question.trim();
    if (!text || controller.current) return;
    const current = new AbortController();
    controller.current = current;
    const timer = window.setTimeout(() => current.abort(), 35_000);
    setBusy(true);
    setError("");
    setMessages(old => [...old, { role: "user", text }]);
    try {
      const response = await fetch("/api/chat", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ question: text }),
        signal: current.signal
      });
      const data: unknown = await response.json();
      if (!isReply(data)) throw new Error("后端响应格式不符合约定。");
      if (!response.ok || data.status !== "answered") {
        throw new Error(`${data.text}（编号：${data.requestId}）`);
      }
      setMessages(old => [...old, { role: "assistant", text: data.text }]);
      setQuestion("");
    } catch (cause) {
      setError(current.signal.aborted ? "请求已取消或等待超时。" :
        cause instanceof Error ? cause.message : "网络请求失败。");
    } finally {
      window.clearTimeout(timer);
      if (controller.current === current) {
        controller.current = null;
        setBusy(false);
      }
    }
  }

  return <main>
    <h1>我的第一只聊天机器人</h1>
    <p>单轮实验：界面保留气泡，本次只发送最新问题。</p>
    <section aria-live="polite">
      {messages.map((m, i) => <article key={i} className={m.role}>
        <strong>{m.role === "user" ? "我" : "助手"}</strong>
        <p style={{ whiteSpace: "pre-wrap" }}>{m.text}</p>
      </article>)}
    </section>
    {error && <p role="alert">{error}</p>}
    <form onSubmit={send}>
      <label htmlFor="question">输入问题</label>
      <textarea id="question" value={question} maxLength={2000} disabled={busy}
        onChange={e => setQuestion(e.target.value)} />
      <button disabled={busy || !question.trim()}>{busy ? "正在回答…" : "发送"}</button>
    </form>
  </main>;
}

setMessages(old => [...old, ...]) 使用之前的状态追加气泡；onSubmit 处理表单提交。这些都是普通 React 状态和事件处理，不需要另学一套“AI 前端语法”。[5]

有几个小细节很值得保留：发送中禁用按钮；用 controller.current 防止同时发出重复请求；失败时保留输入，方便修改；把结果当普通文本显示，而不是塞进 dangerouslySetInnerHTML。

还有一个经典坑：fetch() 不会因为 HTTP 400 或 500 自动进入 catch。因此代码同时检查 response.ok 和业务 status，再决定是否追加助手气泡。isReply 是工程包里的运行时检查，不是一个单纯的 TypeScript 类型断言。[6]

35 秒的前端等待上限和 25 秒的上游请求上限，是本篇的教学设置，不是服务商承诺的响应时间。遇到取消或超时，我们显示错误，不伪造一条成功回答。

七、为什么前端访问 /api/chat，不写 3001？

因为 Vite 开发服务器帮我们转发。完整的 vite.config.ts 如下：

import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  server: {
    host: "127.0.0.1", port: 5173, strictPort: true,
    proxy: { "/api": "http://127.0.0.1:3001" }
  }
});

浏览器请求 5173 端口的 /api/chat，Vite 再把它转给 3001 端口的 Node.js。strictPort 让端口被占用时直接报错，避免悄悄换端口后你还在访问旧地址。[7]

这只是开发代理，不是生产部署方案。上线时要由实际网关或托管平台安排同源路由，或正确配置跨域访问。不要为了“先跑起来”，就把允许来源无限放宽。[7]

本篇两个服务都绑定本机地址。这个学习项目没有账号鉴权和用户级配额，不应直接开放成公共的付费模型入口。

八、把模拟助手换成真实模型

模拟模式跑通后，编辑后端使用的 .env：

MODE=live
OPENAI_API_KEY=填写你自己的密钥
OPENAI_MODEL=填写账号可用且支持Responses接口的模型ID

上面是占位说明，不能原样当成有效配置。不要加 VITE_ 前缀，不要把真实文件提交 Git。

停止并重新运行 npm run server，再发同一个问题。此时才会调用外部模型，可能产生费用；本篇不指定固定价格或保证某个模型在你的账号可用。[1][4]

如果模拟模式成功、真实模式失败，优先看后端日志：模型 ID、密钥、账户权限、网络和输出状态。错误界面会给出请求编号；不要把完整密钥或敏感请求贴进日志。

反过来，如果模拟模式都失败，就先查 3001 服务和 Vite 代理。别在输入框和后端还没连上时，反复修改 Prompt。

九、三个小实验，比“看起来能用”更有说服力

实验一：正常通路。保持模拟模式，发送“你好”。应该先显示等待，再出现明确标注的模拟回复；浏览器不应收到任何 API Key。

实验二：断开后端。停止终端 A，再发送一次。界面应显示错误并恢复可操作状态，而不是永久“正在回答”。实际文案可能由代理错误和响应解析方式决定，不要求固定为某一句话。

实验三：记忆错觉。真实模式下先说“我叫小陈”，再问“我叫什么”。观察 Network：本篇第二次请求仍只包含当前问题，不能据此期待模型知道第一句。即使它碰巧猜对，也不能证明实现了记忆。

文末交互网页还有一个本地流程演示，可以切换成功、拒绝、截断和失败。它不会发请求或调用模型；真正的前后端连通实验，请使用工程包。

十、四道小题，检查你有没有接对线

1. 模型服务的秘密 API Key 放哪里？

A. VITE_OPENAI_API_KEY，方便 React 读取。
B. 可信后端的环境配置中。
C. 给前端代码做一次压缩再放进去。

2. 模拟模式成功，证明什么？

A. 真实模型已经完成鉴权。
B. 机器人具有长期记忆。
C. 本篇的页面与后端请求链路跑通了。

3. fetch 收到 HTTP 500，会自动抛异常吗？

A. 不会仅因 500 自动抛出，需要检查响应状态。
B. 会，所以不需要 response.ok。
C. 不会返回任何 Response。

4. 页面显示了历史气泡，模型就拥有多轮上下文吗？

A. 是，React 状态会自动同步给模型。
B. 不一定，要看本次请求或会话机制实际提供了什么。
C. 只要刷新页面就有。

答案：1B、2C、3A、4B。密钥属于后端；模拟只验证线路；HTTP 状态要主动检查；界面状态和模型上下文不是一回事。

课后练习：给每个失败提示加一个“再次发送”按钮，但仍然只允许一个请求进行中。不要默认循环重试，因为真实模型请求可能计费。

十一、两个你很可能会问的问题

为什么这一篇还不是边生成边显示？

我们刻意先完成普通 JSON 请求：一次发送，一次返回。下一篇再把返回方式改成流式，并处理“收到一部分”与“真正完成”的区别。

模型回答错了，是不是前端没写好？

不一定。先区分线路错误和内容错误：线路通了，只说明请求到了、结果回来了。模型有没有足够证据，仍然是第 13 篇讨论的问题。

本篇只带走这一句话

前端负责交流，后端守住入口，模型负责生成；先把一句话送到，再谈让它记住一百句话。

第 14 篇结束。进度：14 / 40 篇，35%。下一篇：让回答边生成、边显示——流式输出与 SSE。
