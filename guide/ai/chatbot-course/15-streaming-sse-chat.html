上一节，你的网页已经能收到 AI 回复了。

但用户问一个稍长的问题，屏幕就一直显示“正在回答……”——过了几秒，他开始怀疑：是 AI 在思考，还是我家网断了？

今天，我们把“整桌菜做好再上”，改成“做好一道，先上一道”。

不是等答案全部回来，再用定时器假装打字；而是后端收到新内容，就陆续传给页面。 模型接口的流式模式允许这样增量接收输出，不必等整份回答生成结束。[1]

一、先把两个“完成”分清楚

流式聊天里最容易出错的，不是文字显示得慢，而是把没说完的话，当成已经说完。

本篇给页面定两条规矩：收到文字，先显示为草稿；收到明确的完成结果，再标记完成。

收到 delta：追加一点文字，仍是草稿
收到 end：检查最终状态，再决定是否完成
收到 error：显示错误，不伪装成功
连接结束，却没有 end：保留草稿，提示异常结束

delta、end、error 是本篇自己设计的事件名字。尤其是 end，不是 SSE 自动附赠的“成功证明”。

今天仍然只做单轮聊天，不接数据库、历史记忆或工具。先让这条线路能正确开始，也能正确结束。

二、SSE 长什么样？像一张张连续送来的小纸条

SSE（Server-Sent Events）用文本格式传递事件。响应类型是 text/event-stream，内容使用 UTF-8；event: 表示事件名，data: 表示数据，空行分隔事件。[2]

例如，本篇后端会发送这样的内容：

event: delta
data: {"text":"你好，"}

event: delta
data: {"text":"我是你的学习助手。"}

event: end
data: {"status":"answered","text":"你好，我是你的学习助手。"}

前两张纸条只负责追加文字。最后一张说明本次结果，并带回最终正文。

为什么最后还带一份完整文字？这是本篇的选择：用最终正文替换草稿，避免两份结果不一致；不是把完整答案再追加一遍。

end 也可能带 refused 或 incomplete。所以，收到结束事件，只说明“拿到最终状态”，不一定是“拿到完整答案”。

2.1 为什么这里不直接用 EventSource？

浏览器原生 EventSource 很适合按 URL 订阅事件，但构造接口没有任意 POST 请求体和自定义请求头配置。本篇需要 POST 一个问题，因此采用 Fetch 发请求，再读取 SSE 响应体。SSE 数据格式与 EventSource 这个浏览器类，不是一回事。[3]

本篇没有实现自动重连。连接断了就明确告诉用户，不会偷偷重新发起一次可能计费的模型请求。

三、最大的坑：一块网络数据，不等于一条消息

后端写了两条事件，不代表浏览器正好读两次。

一次读取可能拿到两条半；也可能只拿到半条。更麻烦的是，一个中文字符的 UTF-8 字节，也可能跨在两次读取之间。[4][5]

所以，不要把每次拿到的数据都直接 JSON.parse，也不要以为每个网络分块就是一个 Token。

正确的接收顺序是：

收到字节块
   ↓
TextDecoder 连续解码，处理跨块字符
   ↓
暂存未完整的文本行和事件
   ↓
读到事件分隔空行，才取出完整 data
   ↓
解析 JSON、校验字段、更新界面

解码解决“字有没有收完整”；分帧解决“事件有没有收完整”。两步不能少。

配套工程的 shared/sse.ts 实现了这层解析：支持常见换行形式、注释行和多行 data，并限制单个事件大小。没有等到分隔空行的尾部事件，不会因为连接关闭就被当成完整消息。这个做法也符合 SSE 的事件分派规则。[5]

它是本课使用的事件解析器，不是包含自动重连、id 和 retry 全套行为的 EventSource 替代品。

3.1 补充：中文 UTF-8 字节拆开了，怎么正确解码？

在 AI 聊天场景中，如果使用 SSE（Server-Sent Events）或 Fetch Stream 接收流式数据，一个中文字符的 UTF-8 字节可能被拆成两段返回。

例如，中文字符 你 在 UTF-8 中占 3 个字节：

你 = E4 BD A0

第一次收到：E4 BD
第二次收到：A0

如果分别解码，可能出现乱码 �。

1. 错误实现 ❌

const reader = response.body!.getReader();

while (true) {
  const { done, value } = await reader.read();

  if (done) break;

  // 每次独立解码，可能导致中文乱码
  const text = new TextDecoder().decode(value);

  console.log(text);
}

原因：每次创建新的 TextDecoder，无法保留上一次未完成的 UTF-8 字节。

2. 正确实现 ✅

使用 TextDecoder 的流式解码模式 { stream: true }。

const response = await fetch('/api/chat');

const reader = response.body!.getReader();

const decoder = new TextDecoder('utf-8');

while (true) {
  const { done, value } = await reader.read();

  if (done) break;

  // 保留不完整的 UTF-8 字节，等待下一次数据
  const text = decoder.decode(value, {
    stream: true,
  });

  console.log(text);
}

// 处理最后可能残留的字节
const remaining = decoder.decode();

if (remaining) {
  console.log(remaining);
}
原理

假设服务端返回：

Chunk 1: E4 BD
Chunk 2: A0 E5 A5 BD

执行过程：

次数 收到字节 TextDecoder 输出
第一次 E4 BD ""（缓存不完整字符）
第二次 A0 E5 A5 BD "你好"

TextDecoder 会自动缓存未完成的 UTF-8 字节序列。

3. 更推荐：TextDecoderStream

现代浏览器可以直接使用 TextDecoderStream：

const response = await fetch('/api/chat');

const stream = response.body!
  .pipeThrough(new TextDecoderStream());

for await (const text of stream) {
  console.log(text);
}

这样就不需要手动管理 TextDecoder。

工程接入说明（新增，以上补充原文和代码保持不变）：上方代码聚焦解码，使用通用的 GET /api/chat 示例；本课可运行项目使用 POST /api/chat/stream，接入时需沿用工程的请求方式。解码后的字符串还可能是不完整的 SSE 事件，不能直接逐块 JSON.parse；请继续交给事件解析器。项目的 shared/sse.ts 已经在循环外复用 TextDecoder，并在每块解码时设置 stream: true。

页面末尾有“中文分块解码实验”，可逐步查看相同字节在错误与正确解码方式下的结果。

四、后端：不再只调用一次 res.end

上一节，后端等到完整结果再返回 JSON。这一节，它先发送 SSE 响应头，然后用 res.write() 持续写事件，最后再结束响应。

下面是工程中的完整 server/sse.ts：

import { once } from "node:events";
import type { ServerResponse } from "node:http";
import type { Frame } from "../shared/events.ts";

export async function sendSSE(
  res: ServerResponse,
  frame: Frame,
  signal: AbortSignal
) {
  signal.throwIfAborted();
  if (res.destroyed || res.writableEnded) throw new Error("CLIENT_CLOSED");
  const block = `event: ${frame.event}\ndata: ${JSON.stringify(frame.data)}\n\n`;
  if (!res.write(block)) {
    await once(res, "drain", { signal });
  }
}

JSON.stringify 会把正文里的换行编码进 JSON 字符串，不会因为模型回答换了一段，就误变成 SSE 的事件分隔符。

res.write() 返回 false 时，表示需要等写入缓冲恢复，再继续发送。这里等待 drain，而不是无限往内存里塞数据。这叫背压：下游吃不下了，上游先慢一点。[6]

路由文件还负责检查输入、发送响应头、设置超时和处理断连。你不用把这些都塞进一个巨大的 for 循环；工程包里已经分成独立文件。

还有一个重要区别：响应头发出后，不能再把这次 HTTP 200 改成 500。 因此，开流之前的参数错误走普通 HTTP 错误；开流之后的错误，通过本篇的 error 事件告知客户端。[6]

五、模型侧只加 stream: true？还差一步

开启模型接口的 stream: true，只是让它开始流式返回。后端仍要把服务商事件，转换成我们前端认识的事件。

配套工程使用 OpenAI Responses 的文本流，并作如下映射：[1][7]

模型侧信号 本篇后端怎么处理
response.output_text.delta 转成 delta，传递新增文字
response.completed 检查最终响应，再发 end
response.incomplete 发 end，状态为 incomplete
失败事件或上游异常 转为受控的 error 提示

拒绝内容也会从最终响应中识别，不会硬塞成普通成功答案。

特别留意 response.output_text.done：它描述的是某个文本部分结束，不能一看到名字里有 done，就宣布整个请求成功。我们的适配器等待整份响应的结束状态。[7]

本篇只处理普通文本回答，没有注册工具，也不把其他类型事件冒充文字。以后接工具调用，需要扩展协议，不能把每个事件都直接拼进聊天气泡。

六、前端：追加草稿，等到 end 再收工

下面是完整的 src/readChat.ts。它调用工程包里的 SSE 解析器和事件校验器，不需要 React 知道字节怎么拆分。

import { readSSE } from "../shared/sse.ts";
import { parseFrame } from "../shared/events.ts";
import type { End } from "../shared/events.ts";

export async function readChat(
  response: Response,
  onDelta: (text: string) => void,
  signal: AbortSignal
): Promise<End> {
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  if (!response.body || !response.headers.get("content-type")?.includes("text/event-stream")) {
    throw new Error("后端没有返回事件流。");
  }
  let length = 0;
  for await (const item of readSSE(response.body, signal)) {
    const frame = parseFrame(item.event, item.data);
    if (frame.event === "delta") {
      length += frame.data.text.length;
      if (length > 200_000) throw new Error("回答过长，已停止接收。");
      onDelta(frame.data.text);
    } else if (frame.event === "error") {
      throw new Error(frame.data.message);
    } else {
      return frame.data;
    }
  }
  throw new Error("连接已结束，但未收到结束事件；现有文字只是草稿。");
}

最值得记住的是最后一行错误提示：连接结束，不代表回答完成。

在 React 中，只需把增量交给状态更新。下面是 App.tsx 的核心片段，不是完整组件；完整的输入框、按钮、状态和异常处理都在工程包中：

const end = await readChat(response, delta => {
  if (active.current !== controller || controller.signal.aborted) return;
  setText(prev => prev + delta); setState("streaming");
}, controller.signal);
controller.signal.throwIfAborted();
if (end.status === "answered") setText(end.text);

这里使用函数式更新来追加文字，并检查回调是否还属于当前请求。最终完成时则替换全文，不再重复追加。

我们保留 waiting、streaming、answered、refused、incomplete、stopped、failed 等界面状态。用户不仅看到字，还能知道这些字是“正在生成”“已完成”还是“半路中断”。

草稿可以显示，不等于已经通过事实、安全或业务验收。 流式内容在完整输出前就暴露给用户，也会增加内容审核难度；真实产品需要按风险决定哪些内容允许提前展示。[1]

七、停止按钮：不是只让光标停下来

假设你点了“停止”，页面不更新了，但后端还在读模型结果。这更像把扬声器关了，而不是挂电话。

本篇的停止路径是：

点击停止生成
    ↓
浏览器 AbortController.abort("user")
    ↓
中断 Fetch 和响应体读取
    ↓
Node.js 发现下游连接关闭
    ↓
中止上游模型请求，并清理计时器

AbortController 可以中断 Fetch、响应体消费和流读取；后端需要把自己的取消信号继续传给上游请求，而不只是修改一个 React 状态。[8]

我们的组件卸载时也会取消，且保留同一请求的标识，避免已经结束的回调继续写入当前界面。

本课不会把“用户主动停止”显示成“回答完成”。已经收到的文字保留下来，但标为未完成草稿。也不承诺取消能撤销服务商已经完成的计算或费用。

在终端 A 中运行：

默认 MODE=mock。输入“你好”，你会看到带有“模拟流，未调用模型”标记的文字分段出现。这是本地定时发送的测试数据，用来验证网络与界面，不是模型生成效果。

页面下拉框还可以切换“生成上限”“拒绝”“流中错误”“无结束事件就断线”。最后一种故意不发送 end，用来检查页面有没有把断线误判成完成。

九、文字为什么仍然攒到最后一起出现？

别马上怪 React。先沿着这条链路看：模型有没有逐步返回，Node.js 有没有逐步写出，代理有没有缓存，浏览器有没有逐步读取。

例如 Nginx 的代理缓冲可能把上游内容暂存起来；它可以通过配置关闭，也可能响应 X-Accel-Buffering: no，但是否生效取决于实际代理配置。一个响应头，不会自动关闭整条链路上的所有缓冲。[9]

res.flushHeaders() 只负责提前发送响应头，也不能让还没生成的字提前出现，更不能保证每次 write() 都对应浏览器的一次读取。[6]

先做三个小实验：正常结束后应是 answered；中途点击停止应是 stopped；没有结束事件就断线应保留草稿并提示失败。再去比“每秒显示几个字”，才有意义。

工程里前端 35 秒、上游 25 秒的超时都是教学设置，不是性能承诺。它没有自动重连、断点续传、持久化或用户级限流，不能直接作为面向公网的付费服务。

十、课后测验：你能分清“收到”和“完成”吗？

1. reader.read() 返回 done: true，说明什么？

A. 响应体没有更多数据；仍要检查有没有业务结束事件。
B. 模型回答一定完整。
C. 答案里的事实都正确。

2. 一个中文字符的字节被拆到两块数据里，怎么办？

A. 每块单独解码，出现乱码再删除。
B. 用连续解码器处理字节，再缓冲并解析完整事件。
C. 强制每次请求只允许英文。

3. 这篇为什么用 Fetch 接收 SSE？

A. SSE 不能在浏览器使用。
B. EventSource 会自动把答案变正确。
C. 本篇需要 POST 问题，并自行管理请求与流读取。

4. 真正的“停止生成”应做什么？

A. 只停止更新 React 状态。
B. 中断客户端请求，并让后端把取消传给上游。

十一、两个常见问题

流式输出能让模型总共算得更快吗？

它首先改变的是交付方式：用户不必等全部内容生成完才看到开头。总耗时仍受模型、排队、网络和输出长度等因素影响，不能保证一开流式就整体加速。[1]

既然能边显示，能不能边执行回答里的代码？

本课不这么做。未完成文字既可能被截断，也可能错误；内容完成也不等于获得操作授权。我们只显示文本，不执行模型输出。

本篇只带走这一句话

收到一点就展示一点，但只有真正完成，才说“完成”；用户叫停，整条链路都要听见。
