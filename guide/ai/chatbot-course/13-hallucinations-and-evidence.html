📘 第 13 篇：AI 说得像真的，怎么知道它没在编？

幻觉、证据与答案核验｜第 13 / 40 篇｜阅读约 10–12 分钟

上一篇，我们让 AI 从“写小作文”改成“按表格回答”。

现在，表格整整齐齐，引用一应俱全，代码看起来也像那么回事。

你复制运行，控制台却回你一句：

TypeError: sdk.autoFixLogin is not a function

格式验收过了，事实还没验收。

这一篇，我们给聊天机器人加一道检查：你说的每个关键结论，证据在哪里？

一、先看一个“看起来很专业”的错误

假设你正在做一个 SDK 问答助手，手里只有两段资料。以下 SDK、资料和回答都是教学设定，不是你公司真实接口的说明。

S1： 本项目 v2 的 Token 校验必须由服务端完成，前端不得保存服务端密钥。
S2： 登录失败后，最多重试 2 次。

用户问：“登录失败怎么办？”

AI 回答：

SDK 默认自动重试两次，还可以调用 sdk.autoFixLogin() 一键修复。为了方便，前端也能保存服务端密钥。来源：S1、S2。

读起来挺顺，仔细一看却有三个问题：

“最多重试两次”被说成了“默认自动重试两次”；资料没提到的方法，被当成现成接口；“不得保存”被说成了“可以保存”。

本篇关注的幻觉，就是这种把错误或缺乏依据的内容，当作事实说出来的情况，包括与给定资料不一致的回答。不是看到 AI 写了虚构故事就叫幻觉——用户本来就在要求创作时，虚构是任务的一部分。[1]

二、它为什么能把错话说得这么圆？

2.1 学会“怎么说”，不等于每次都“查过了”

语言模型在预训练中学习预测后续 Token，而不是为输出的每句话自动附上一张“事实核验通过”的证明。模型可以学到知识和推理能力，但这种生成过程本身不保证每个细节都真实。[2]

比如，sdk.autoFixLogin() 很像一个合理的 API 名称。

合理的名字、熟悉的代码结构、流畅的解释，拼在一起，就可能让一段没有依据的回答看起来特别像官方文档。

像一个答案，和是正确答案，是两件事。

2.2 有些评分方式，还会鼓励“不知道也猜一个”

想象一次考试：答错零分，空着也零分。不会做时，蒙一个还有机会得分。

OpenAI 的研究指出，偏重答对率、不给恰当的不确定性留位置的训练与评估激励，会鼓励猜测。这是幻觉持续存在的一个重要解释，不是所有错误的唯一原因。[2]

所以，开发机器人时，别只考核“它回答了多少问题”，也要考核“它有没有把不知道的事情说成知道”。

三、先学会分三种情况，别急着判“真或假”

继续使用 S1、S2。我们只判断：这些资料是否支持下面的话？

待核对的结论 判定 为什么
本项目登录失败后，最多重试 2 次 有依据 S2 明确写了上限
SDK 默认自动重试 2 次 证据不足 上限不是默认行为，也没有说明自动执行
本项目允许前端保存服务端密钥 与资料冲突 S1 明确说“不得”
SDK 提供 autoFixLogin() 证据不足 两段资料都没有介绍这个接口

最容易踩坑的是最后一行：

“资料没写”不等于“这个功能肯定不存在”。

你能得出的结论是“目前无法确认”，不是把一个未知答案硬改成“没有”。同样，回答与资料一致，也不自动证明资料本身正确；还要确认资料的版本、时效和适用对象。

记住三个标签就够了：有依据、冲突、证据不足。

四、别给整篇作文打分，要逐条核对结论

一句话可能一半对、一半没依据：

登录失败最多重试两次，并且会自动刷新 Token。

前半句由 S2 支持，后半句没有对应资料。不能因为前半句正确，就给整句话盖章。

这种“把长回答拆成小事实，再逐条检查”的思路，也用于 FActScore 等事实性评估研究。一段回答可能混合了有依据和无依据的信息，简单判整段对或错，会丢失细节。[3]

实际核对时，我建议连问三句：

引用是真的吗？原文真这么写吗？原文支持的是这句结论吗？

其中第三句最关键。哪怕把 S2 一字不漏地引用出来，它也不能证明“自动重试”。引用不是装饰性的脚注，而是结论和依据之间的连接。

对于你的技术助手，还要多留意一个词：版本。v1 的接口说明，不能不加说明地拿来回答 v2 的接入问题。

五、RAG 是开卷考试，不是标准答案

RAG 把相关资料找来，让模型参考它们作答。你可以把它想成开卷考试：书拿到了，但仍可能翻错页、看漏“不得”，或给原文加上自己的猜测。

因此，我建议把“检索后直接回答”改成下面这个小流程：

找到相关资料
    ↓
检查版本与适用范围
    ↓
列出准备回答的关键结论
    ↓
给每条结论寻找支持原句
    ↓
能确认的回答；冲突的改正；缺依据的说明缺口

允许模型承认信息不足、先摘取原句、再按结论核对引用，是官方文档建议的减幻觉方法；这些方法降低风险，但不保证错误归零。[1]

下面是一段可放进你的问答系统的教学提示词：

请只根据本次提供的资料回答具体接口问题。

每个关键结论都应对应资料中的支持原句。
区分“明确支持”“明确冲突”“资料未说明”。
不要把“最多”改成“默认”，不要把“可以”改成“必须”。
资料未说明的方法名，不要自行补成真实接口。
能回答一部分，就先回答那部分，再说明还缺什么。

这段提示词不是事实保险，更不是权限系统。它只是让任务更明确；检查结果仍然需要验证。[1]

六、TypeScript：先写一个小小的“回答闸门”

我们先不造一个万能事实验证器，只做一件简单的事：根据已经得到的核对结果，决定下一步怎么处理。

// 核对结果应来自上游评审，不是让模型自行声明“我正确”。
type Check = {
  claim: string;
  verdict: "supported" | "contradicted" | "insufficient";
};

export function chooseAction(checks: readonly Check[]): string {
  if (checks.length === 0) return "补充材料或完成核对";

  if (checks.some(c => c.verdict === "contradicted")) {
    return "撤回冲突结论，重写后再核对";
  }

  if (checks.every(c => c.verdict === "supported")) {
    return "按已核对的结论回答";
  }

  if (checks.some(c => c.verdict === "supported")) {
    return "只回答有依据的部分，并说明缺口";
  }

  return "说明证据不足，不猜测";
}

console.log(chooseAction([
  { claim: "最多重试两次", verdict: "supported" },
  { claim: "默认自动重试", verdict: "insufficient" }
])); // 只回答有依据的部分，并说明缺口

这段代码没有判断一句话是不是真的。 它只处理评审结果。上游需要覆盖答案中的全部关键事实，并用原文、确定性检查或人工复核来核对；模型辅助评审也可能判断错。

例如检查某个 API：可以核对指定版本的官方文档、类型定义和测试。某一项检查通过，也不要扩大成“整段答案都正确”。

重写后新增了结论，就要检查新增的内容，不能拿旧回答的验收结果给新回答背书。这是本篇的处理规则。

七、“不知道”也可以说得有用

差的回答：

不知道。

仍然差的回答：

不太确定，但应该可以调用 sdk.autoFixLogin()。

加上“不太确定”，并没有给这个接口补出证据。

基于本篇资料，更好的回答是：

本项目规定，登录失败后最多重试两次；Token 校验由服务端完成，前端不得保存服务端密钥。

当前资料没有说明重试是否自动执行，也没有介绍修复接口。需要补充对应版本的重试配置和 API 文档，才能确认实现方式。

它没有全部拒答，也没有硬凑一个“完整方案”。

把确定的交付，把不确定的标清。 这就是本篇希望机器人采取的回答方式。

八、怎样知道机器人真的变可靠了？

假设你准备了 20 个测试问题，下面是两套方案的结果。数据是教学示例，不是任何模型的实测成绩。

结果 方案 A：每题都答 方案 B：没把握时暂不答
回答了多少题 20 15
答对多少题 15 14
答错多少题 5 1
暂未回答 0 5
已回答问题的正确率 75% 约 93.3%

B 的错误更少，但它也少答对了一题；不能只拿“93.3%”就宣布全面胜出。

我的建议是同时看：答对多少、答错多少、遗漏多少。 对原本有依据的问题无故不答，也要计入质量问题。这样才不会把一个永远说“不知道”的机器人评成优等生。

工程练习可以从四个样本开始：正常资料、缺少关键资料、混入旧版本、原文包含否定条件。每次改 Prompt 或检索策略，都重新跑一遍，别只凭“这次看起来聪明了”。

九、课后测验：这次你来当事实检查员

第 1 题：资料写“最多重试两次”，能确认什么？

A. SDK 默认自动重试两次。
B. 重试次数上限是两次。
C. 每次失败必须重试两次。

第 2 题：没有找到某个方法的介绍，应该怎么说？

A. 这个方法一定不存在。
B. 根据命名规律补一个用法。
C. 当前资料不足以确认，需要对应版本文档。

第 3 题：引用原文确实存在，就说明答案有依据吗？

A. 不一定，还要核对原文是否支持具体结论。
B. 是，找到同一句话就行。
C. 是，只要引用数量足够多。

第 4 题：为什么不能只看“已回答问题的正确率”？

A. 这个指标完全没有用。
B. 还要看覆盖了多少问题，避免通过大量不回答抬高分数。
C. 应该只看回答速度。

答案：1B、2C、3A、4B。

第一题不能把上限变成默认行为；第二题不能把未知变成否定；第三题区分“引用存在”和“支持结论”；第四题提醒我们，可靠与有用都要评估。

动手练习： 把“最多重试 2 次”改为“仅在网络超时时最多重试 2 次”。再检查原来的答案。发现了吗？次数没变，但适用条件变了；遗漏这个条件，同样会误导用户。

十、两个容易误会的地方

让 AI 再检查一遍，就能放心了吗？

不能把它当成保证。研究中，自我检查的效果会因任务和方法而不同，有些设置改善结果，有些反而变差。比起只问“你确定吗”，本篇更建议让检查围绕具体原文、版本和测试结果展开。[4]

模型说“我有 99% 把握”，可以直接放行吗？

本篇不会用这句话放行。这个数字没有经过你自己的校准与验证；而且把同一句话重复说三遍，也没有增加新的证据。我们的检查对象是结论和依据，不是语气。

本篇只带走这一句话

不要只问 AI“你确定吗”，要问“哪条证据，支持你哪句话？”

配套练习：你来核对证据

固定样本，本地交互，不调用模型，不自动验证任意文字。

S1：本项目 v2 的 Token 校验必须由服务端完成，前端不得保存服务端密钥。

S2：登录失败后，最多重试 2 次。

1. 本项目登录失败后，最多重试两次。
2. SDK 默认自动重试两次。
3. 本项目允许前端保存服务端密钥。
4. SDK 提供 autoFixLogin() 方法。
5. 只有网络超时才可以重试。
