Token 与 Embedding：为什么 AI 能把文字变成数学？

上一篇我们学习了 ChatGPT 的基本工作流程：

用户输入 → Tokenization → Transformer → 预测下一个 Token → 生成回答。

但这里留下了一个非常关键的问题：

计算机只认识数字，为什么 ChatGPT 能理解「苹果是一种水果」，甚至知道「苹果」和「香蕉」在语义上比较接近？

答案就藏在今天的两个核心概念里：

  • Token：把文本拆分成模型能够处理的单位。

  • Embedding：把这些单位转换为具有语义信息的数字向量。

一、Token：AI 眼中的文字

假设你向 ChatGPT 输入：

我是一名前端开发工程师。

模型并不是直接处理这个字符串，而是先通过 Tokenizer 将其转换为 Token ID。

第一步：文本分词（示意）

我是一名前端开发工程师

我

是一名

前端

开发

工程师

123

456

789

234

567

以上分词和 ID 均为示意，并非真实模型输出

为什么不直接按照汉字分词？

因为模型需要兼顾多种语言、代码、数字以及特殊符号。

例如：

纯文本
JavaScript useState console.log() 你好世界 2026-10-15

不同的 Tokenizer 可能采用不同的拆分策略，例如 BPE（Byte Pair Encoding）。

它们通常会让常见的文本片段对应较少的 Token，而不常见的片段可能需要拆成多个 Token。

这也解释了为什么：

Token 数量不等于字数，也不等于单词数。

二、Embedding：把文字转换成向量

这是今天最重要的知识点。

假设 Tokenizer 将「苹果」转换成 ID：

纯文本
苹果 → 1024

问题来了：

1024 这个数字能够代表「苹果」的含义吗？

不能。

它只是一个编号，就像数据库中的主键。

SQL
SELECT * FROM words WHERE id = 1024;

ID 本身不包含「苹果是一种水果」的语义。

所以我们还需要一个步骤：

Embedding（嵌入表示）。

Embedding 会将离散的 Token ID 映射成连续的数字向量。

例如：

纯文本
苹果 → [0.82, 0.71, 0.13, ...] 香蕉 → [0.79, 0.75, 0.18, ...] 汽车 → [0.12, 0.09, 0.91, ...]

这些数字只是为了演示。

真实大模型的 Token Embedding 往往包含数百到数千个维度，具体取决于模型架构。

而且向量的单个维度通常没有固定的人类可解释含义，语义信息分布在多个维度的组合之中。

三、为什么向量能够表示语义？

想象我们有三个词：

  • 苹果

  • 香蕉

  • 汽车

经过某个语义 Embedding 模型编码后，假设得到如下二维投影：

语义向量空间（概念示意）

这是人为绘制的二维概念图，不是真实 Embedding 模型的计算结果。

你会发现：

「苹果」与「香蕉」的距离比较近，而「汽车」离它们比较远。

因为在语义上：

  • 苹果和香蕉都属于水果。

  • 汽车属于交通工具。

需要注意，这种关系并不是程序员手动编写的：

JavaScript
if (word === "苹果") {
  category = "水果";
}

而是模型通过训练，从大量数据中学习到的。

当然，实际语义空间远比二维图复杂，词语也可能有多种含义，例如「苹果」还可能指一家科技公司。

四、Embedding 是如何学习出来的？

这里需要区分两种相关但不同的概念。

第一种：LLM 内部的 Token Embedding。

它通常通过语言模型的训练目标，与 Transformer 的其他参数一起被优化。

例如，模型不断练习预测下一个 Token，训练过程中通过反向传播调整参数，逐步形成有用的表示。

第二种：用于语义搜索的 Embedding 模型。

这种模型通常专门训练来表示文本片段的语义关系。

例如：

纯文本
问题 A：如何使用 React 管理状态？ 问题 B：React 的状态管理怎么做？ 问题 C：广州今天的天气如何？

理想情况下，A 和 B 的向量相似度比较高，而 A 和 C 的相似度比较低。

这类模型常使用对比学习等方法，让相关文本的向量更接近、不相关文本的向量更容易区分。

因此，不要把 LLM 内部的 Token Embedding 和知识库检索使用的文本 Embedding 完全等同。

五、如何计算两个向量的相似度？

在实际工程中，常用一种方法：

Cosine Similarity（余弦相似度）。

公式如下：

sim⁡(A,B)=A⋅B∥A∥∥B∥\operatorname{sim}(A,B)=\frac{A\cdot B}{\|A\|\|B\|}sim(A,B)=∥A∥∥B∥A⋅B​

它衡量的是两个向量方向上的接近程度。

对于非零向量，结果范围为 -1 到 1。越接近 1，说明方向越一致。

你可以自己调整下面的两个向量，观察相似度如何变化。

在实际的 RAG 系统中，可能会计算：

纯文本
用户问题 Embedding ↓ 与知识库中的向量比较 ↓ 找出最相似的文本片段 ↓ 将相关内容交给 LLM ↓ 生成回答

这里要特别注意：向量相似度高，不等于事实正确，也不一定代表检索结果真正相关。

因此生产级 RAG 系统通常还需要重排序、过滤和答案评估。

六、TypeScript 如何使用 Embedding？

假设我们希望实现一个简单的语义搜索系统。

可以使用 Embedding API 将文本转换为向量。

下面以 OpenAI 的 Embedding API 为例：

TypeScript

import OpenAI from "openai";

const client = new OpenAI();

async function getEmbedding(text: string) {
  const result = await client.embeddings.create({
    model: "text-embedding-3-small",
    input: text,
  });

  return result.data[0].embedding;
}

const vector = await getEmbedding(
  "如何使用 React 管理状态？"
);

console.log(vector.length);

text-embedding-3-small 默认返回 1536 维向量。

你可以将这些向量保存到 PostgreSQL + pgvector、Qdrant 或其他支持向量检索的数据库中。

这里还有一个工程细节：查询向量和文档向量应使用兼容的 Embedding 模型及配置，否则计算出的相似度可能没有实际意义。

八、Embedding 和 Transformer 的关系是什么？

这是一个很容易混淆的地方。

大语言模型内部的数据流（简化版）

用户输入

我喜欢 JavaScript

Tokenizer

文本 → Token ID

Token Embedding

Token ID → 高维向量

Transformer

Attention + 前馈网络等

输出层

计算下一个 Token 的概率

生成回答

将生成的 Token 解码为文字

可以把它们理解成不同的职责：

Tokenizer 负责将文本转换成编号。

Embedding 负责把编号转换成模型能够计算的向量表示。

Transformer 负责结合上下文，对这些表示进行多层计算。

输出层 负责把模型计算结果转换成下一个 Token 的概率分布。

需要注意，Transformer 内部还会加入位置信息，Token 的表示也会随着网络层数不断变化，并不是一个固定的向量从头用到尾。

九、实际工程中什么时候需要 Embedding？

对于你未来开发的 AI 聊天机器人，可以分成三种情况。

应用场景

是否需要单独调用 Embedding API

普通聊天机器人

通常不需要

多轮聊天机器人

通常不需要

企业知识库问答（RAG）

通常需要

为什么普通聊天不需要？

因为你调用 LLM API 时，模型服务内部已经完成了 Tokenization、Embedding 和推理过程。

只有当你需要语义搜索、知识检索、相似内容匹配等能力时，才通常需要单独使用 Embedding 模型。

例如，开发一个企业内部 AI 助手：

纯文本
员工提问： 公司的统一登录 SDK 如何接入？ ↓ Embedding 模型 ↓ 生成问题向量 ↓ 向量数据库检索 ↓ 找到相关 SDK 文档 ↓ 将文档作为上下文发送给 LLM ↓ 生成带有文档依据的回答

这就是 RAG 的基础思路。

概念

Token ID

第 03 篇：《Transformer 与 Attention：ChatGPT 为什么能理解上下文？》

我们会重点讲解 Self-Attention、Q/K/V、位置编码、因果掩码，以及为什么 Transformer 比传统 RNN 更适合大规模语言模型。

学习疑问与解答：向量方向与投影方向

对，你的理解基本正确，但需要区分「向量方向」和「投影方向」。

在 Embedding 中：

  • 向量方向：可以反映语义特征，不同方向可能对应不同的语义关系。

  • 投影方向：只是我们选择从哪个角度观察高维向量，不会改变向量本身的语义。

一、为什么不同方向可能代表不同语义？

假设我们人为设计一个二维语义空间：

  • X 轴：水果属性，越往右越接近水果。

  • Y 轴：交通工具属性，越往上越接近交通工具。

人为定义坐标轴的教学示意图，真实 Embedding 不会自动为每个维度分配明确的语义标签。

在这个例子中：

  • 苹果和香蕉的向量方向比较接近，因此语义比较相似。

  • 汽车的向量方向与它们不同，因此语义差异较大。

但真实 Embedding 通常有几百甚至几千维，语义信息分布在多个维度中，不能简单理解为「第 1 维代表水果，第 2 维代表交通工具」。

二、为什么投影方向不同，看到的语义关系也可能不同？

假设我们有一个 1536 维的 Embedding 向量。

人类无法直接观察 1536 维空间，所以需要将它投影到二维。

如果选择不同的投影方式，二维图中的点可能呈现不同的距离和聚类关系。

但是，原始的 1536 维向量没有变化。

因此：

  • 不同投影可能突出不同的语义特征。

  • 降维可能丢失部分语义关系。

  • 不能仅凭二维图中两个点靠得近，就断言它们在原始高维空间中也同样接近。

三、还有一个更重要的概念：语义方向

在某些 Embedding 空间中，我们可以研究两个向量的差：

D=E(国王)−E(男人)D = E(\text{国王})-E(\text{男人})D=E(国王)−E(男人)

这个差向量可能捕捉到某些与性别、身份相关的语义变化。

经典词向量研究中存在类似的类比现象，但它并不是所有 Embedding 模型都能稳定满足的数学规律。

所以可以这样总结：

向量的位置与方向可能编码语义信息；不同的投影只是从不同角度观察这些信息，并不创造新的语义。

你可以把它想象成：一个三维物体，从正面看和侧面看形状不同，但物体本身并没有改变。

下一步最值得理解的是：既然每个 Token 最初都有自己的 Embedding，那么 Transformer 是怎么让同一个「苹果」在「吃苹果」和「苹果发布 iPhone」中表现出不同语义的？

这正是下一篇 Attention 机制要解决的问题。
