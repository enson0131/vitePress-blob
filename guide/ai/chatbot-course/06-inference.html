2.1 Prefill 是什么？

Prefill 可以理解为模型处理已经提供的上下文的阶段。

假设用户输入：

纯文本

模型需要对这些 Token 进行计算。

在标准 Transformer 中，Prefill 阶段可以对输入序列中的多个位置并行执行矩阵运算。

但这里有一个细节：

并行处理不代表所有 Token 可以互相看到。

对于 GPT 这类因果语言模型，Causal Mask 仍然限制每个位置只能访问当前位置及之前的 Token。

2.2 Prefill 为什么可能很慢？

假设用户发送：

  • 100 Tokens 的问题。

  • 10,000 Tokens 的聊天历史。

  • 50,000 Tokens 的文档。

那么模型需要处理的输入上下文就可能非常长。

上下文越长，Prefill 通常需要更多计算资源。

因此，AI 聊天机器人的响应速度，不只取决于输出长度，也取决于输入上下文长度。

3.1 为什么不一次性生成整个回答？

因为自回归语言模型的下一个 Token 预测依赖此前已经生成的 Token。

数学上可以表示为：

P(x1,…,xn)=∏t=1nP(xt∣x<t)P(x_1,\ldots,x_n)=\prod_{t=1}^{n}P(x_t\mid x_{<t})P(x1​,…,xn​)=t=1∏n​P(xt​∣x<t​)

也就是说：

第 2 个 Token 依赖第 1 个，第 3 个依赖前两个，以此类推。

不过，这不代表模型内部所有计算都是串行的。单次前向传播中的矩阵运算仍然可以高度并行。

3.2 Decode 什么时候结束？

通常包括以下情况：

  • 模型生成结束标记。

  • 达到最大输出 Token 限制。

  • 命中停止序列。

  • 请求被取消或中断。

四、KV Cache：为什么生成速度能够提升？

还记得第 03 篇的 Q、K、V 吗？

Q=XWQ,K=XWK,V=XWVQ=XW_Q,\quad K=XW_K,\quad V=XW_VQ=XWQ​,K=XWK​,V=XWV​

在 Attention 中，Query 会与 Key 计算匹配分数，再对 Value 进行加权聚合。

问题是：

生成一个新 Token 时，是否需要重新计算全部历史 Token 的 K 和 V？

如果不使用缓存，朴素实现可能重复计算大量历史内容。

于是出现了 KV Cache。

4.1 KV Cache 的工作方式

KV Cache 复用过程

第一步：Prefill 计算已有 Token 的 K/V

K₁,V₁

K₂,V₂

K₃,V₃

第二步：生成新 Token，计算新的 K/V

K₁,V₁

K₂,V₂

K₃,V₃

K₄,V₄

复用历史 K/V，计算新 Token 的 Attention

这就是 KV Cache 的核心价值：

用额外的存储空间，减少重复计算。

4.2 KV Cache 的代价是什么？

它需要消耗显存。

假设模型有：

  • 32 层 Transformer。

  • 32 个 KV Heads。

  • 每个 Head 的维度为 128。

  • 上下文长度为 4,096。

  • 使用 FP16（每个元素 2 字节）。

KV Cache 的简化估算公式：

M=2×L×Hkv×D×N×BM=2\times L\times H_{kv}\times D\times N\times BM=2×L×Hkv​×D×N×B

代入后：

M=2×32×32×128×4096×2M=2\times32\times32\times128\times4096\times2M=2×32×32×128×4096×2

示例 KV Cache 占用

2 GiB

单条序列，假设全部缓存采用 FP16，不含其他显存开销

因此，长上下文和高并发都会对推理服务造成显存压力。

另外，现代模型可能使用 GQA、MQA、滑动窗口注意力、KV Cache 量化等技术降低成本。

五、Temperature：为什么同一个问题会得到不同回答？

Temperature 控制的是这个分布的集中程度。

Pi=softmax⁡(zi/T)P_i=\operatorname{softmax}(z_i/T)Pi​=softmax(zi​/T)

其中：

  • ziz_izi​：第 i 个 Token 的 Logit。

  • TTT：Temperature。

  • PiP_iPi​：调整后的概率。

七、推理性能：TTFT、TPS 与延迟

7.2 为什么输出到一半时可能变慢？

首先要理解一个关键区别：

Prefill 通常更偏向计算密集型，而 Decode 在很多部署场景下更容易受到内存带宽限制。

这是因为在 Decode 阶段，模型通常需要逐 Token 执行前向计算，并访问模型权重和 KV Cache。

假设：

纯文本
用户提问 ↓ Prefill：处理 2,000 Tokens ↓ Decode：生成 1,000 Tokens

Decode 需要执行多轮生成。

而且随着生成长度增加，KV Cache 也可能不断增长。

但这里有个容易误解的地方：

生成越往后，并不意味着 TPS 一定持续下降。

真实推理性能还受到批处理策略、注意力实现、硬件、服务端负载以及缓存管理方式影响。

7.3 如何计算生成速度？

假设模型在首 Token 之后，用 8 秒生成了 400 个额外 Token。

那么：

TPS=4008=50TPS=\frac{400}{8}=50TPS=8400​=50

即每秒生成 50 Tokens。

import express from "express";
import OpenAI from "openai";

const app = express();
const client = new OpenAI();

app.use(express.json());

app.post("/api/chat", async (req, res) => {
  const message = req.body?.message;

  if (typeof message !== "string" ||
      !message.trim() ||
      message.length > 10000) {
    res.status(400).json({
      error: "Invalid message"
    });
    return;
  }

  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.setHeader("Cache-Control", "no-cache");
  res.flushHeaders();

  const controller = new AbortController();

  res.on("close", () => {
    if (!res.writableEnded) controller.abort();
  });

  try {
    const stream = await client.chat.completions.create(
      {
        model: "gpt-4.1-mini",
        messages: [
          { role: "user", content: message }
        ],
        stream: true
      },
      { signal: controller.signal }
    );

    for await (const chunk of stream) {
      if (controller.signal.aborted) break;

      const content =
        chunk.choices[0]?.delta?.content;

      if (content) res.write(content);
    }

    if (!res.writableEnded) res.end();
  } catch (error) {
    console.error(error);
    if (!res.writableEnded) res.end();
  }
});

app.listen(3000);

这个示例使用原始文本流，方便理解原理，并不是严格的 SSE 事件格式。

在生产环境中，还需要增加用户鉴权、请求限流、错误事件协议、日志和持久化等机制。

尤其需要注意：响应头已经发送后，不能再像普通 JSON API 一样随意修改 HTTP 状态码。

8.3 React 前端实现流式渲染

接下来，我们使用 Fetch API 的 ReadableStream 读取响应。

TypeScript

import { useRef, useState } from "react";

export function Chat() {
  const [message, setMessage] = useState("");
  const [answer, setAnswer] = useState("");
  const [loading, setLoading] = useState(false);

  const controllerRef =
    useRef<AbortController | null>(null);

  async function sendMessage() {
    if (!message.trim() || loading) return;

    const controller = new AbortController();
    controllerRef.current = controller;

    setLoading(true);
    setAnswer("");

    try {
      const response = await fetch("/api/chat", {
        method: "POST",
        headers: {
          "Content-Type": "application/json"
        },
        body: JSON.stringify({ message }),
        signal: controller.signal
      });

      if (!response.ok || !response.body) {
        throw new Error("Request failed");
      }

      const reader = response.body.getReader();
      const decoder = new TextDecoder();

      while (true) {
        const { done, value } = await reader.read();

        if (done) break;

        const text = decoder.decode(value, {
          stream: true
        });

        setAnswer(prev => prev + text);
      }

      const tail = decoder.decode();
      if (tail) setAnswer(prev => prev + tail);
    } catch (error) {
      if (!controller.signal.aborted) {
        console.error(error);
      }
    } finally {
      setLoading(false);
      controllerRef.current = null;
    }
  }

  function stopGeneration() {
    controllerRef.current?.abort();
  }

  return (
    <div>
      <textarea
        value={message}
        onChange={e => setMessage(e.target.value)}
      />

      <button onClick={sendMessage}>
        发送
      </button>

      <button onClick={stopGeneration}>
        停止生成
      </button>

      <div>{answer}</div>
    </div>
  );
}

这里最重要的代码是：

TypeScript
const reader = response.body.getReader();

它允许前端逐块读取响应数据。

每收到一块数据，就更新 React 状态：

TypeScript
setAnswer(prev => prev + text);

因此，用户可以看到文字逐步出现。

但有一个非常重要的区别：

网络 Chunk 不等于 Token。

一次网络 Chunk 可能包含多个 Token，也可能只包含一个 Token 的部分 UTF-8 字节。

这也是为什么我们使用 TextDecoder 并开启 stream: true。

9.2 为什么需要限制上下文长度？

假设一个聊天机器人有 100 轮历史消息。

如果每次请求都把所有历史消息发送给模型，就可能出现：

纯文本
第 1 轮： 100 Tokens 第 2 轮： 300 Tokens 第 3 轮： 500 Tokens ... 第 100 轮：20,000 Tokens

这会增加输入 Token 成本和 Prefill 计算负担。

实际应用通常需要结合：

  • 最近消息窗口。

  • 历史对话摘要。

  • 相关记忆检索。

  • 系统提示词缓存。

这些属于应用层上下文管理，与模型内部的 KV Cache 并不是一回事。

十、本篇总结

我们把今天学习的知识串联起来：

1

Prefill

处理已有输入上下文

2

Decode

逐步生成下一个 Token

3

KV Cache

缓存历史 Key / Value，减少重复计算

4

Temperature / Top-p

控制 Token 采样策略

5

Streaming

把生成内容增量传输给客户端

最重要的一句话：

模型通过 Prefill 理解已有上下文，通过 Decode 逐 Token 生成内容，通过 KV Cache 提升推理效率，而聊天应用通过 Streaming 将生成结果实时呈现给用户。
