模型推理：ChatGPT 为什么一个 Token 一个 Token 地回答？

上一篇我们学习了预训练、SFT 和偏好对齐。模型训练好之后，用户输入问题，它是如何在几秒钟内给出回答的？这就是 Inference（推理）。本篇重点认识 Prefill、Decode、KV Cache、Temperature、Top-p，以及聊天产品中的流式输出。

一、推理不是训练

训练通过梯度更新权重；普通推理使用固定的模型权重，结合当前输入预测后续 Token。你在对话里纠正一次答案，不等于模型权重立刻改变。

一次聊天请求的完整路径
用户发送消息
↓
Tokenizer → Token IDs
↓
Prefill：处理已有输入上下文
↓
Decode：预测一个新 Token → 重复
↓
Token 解码为文本 → 流式显示

二、Prefill：先读懂已经给出的上下文

假设用户输入「请解释 React 的 useEffect」。模型首先处理 System Prompt、历史消息与当前问题等已有输入。这个阶段称为 Prefill，它可以对输入中的多个位置进行并行计算，并建立后续可复用的注意力缓存。

Prefill 不等于把整段问题转换为一条人工编写的摘要；它是 Transformer 对输入序列执行计算。已有上下文越长，Prefill 通常越耗时，但性能也取决于硬件、模型结构与服务端优化。

三、Decode：逐 Token 生成答案

Prefill 后，模型根据当前上下文预测下一个 Token。选出一个 Token 后，把它加入序列，再预测下一个。直到输出结束标记、达到长度限制或满足其他停止条件。

自回归解码过程
已有上下文：「React 是」
↓ 预测
生成：「一个」
↓ 再预测
生成：「用于」
↓ 继续
生成：「构建 UI 的库……」
分词结果仅为概念示意，真实 Tokenizer 不一定按这些词切分。

这里的「逐 Token」指生成依赖关系，并不意味着所有推理计算都只能串行执行。模型内部的大量矩阵运算仍可并行。

四、KV Cache：为什么不用每次重新计算全部历史？

在前面的课程中，我们知道 Attention 使用 Q、K、V。自回归解码时，过去 Token 的 K/V 在标准因果注意力中可复用。因此服务端可以保存各层历史位置的 K 和 V；生成下一个 Token 时，只计算新位置所需的表示并读取历史缓存。

KV Cache 的复用示意
Prefill：计算输入序列的 K / V
↓ 保存
缓存：[K₁,V₁] [K₂,V₂] [K₃,V₃]
↓ 生成新 Token
新增 [K₄,V₄]，复用历史 K/V
缓存按层管理；不同模型的 GQA、MQA、滑动窗口注意力和缓存策略会影响具体内存占用。

代价：KV Cache 占用显存或其他存储资源，长上下文与高并发时可能成为重要瓶颈。缓存不会让注意力计算完全消失。

五、Temperature：为什么同一个问题会得到不同回答？

模型先计算候选 Token 的 logits，再通过采样策略选择输出。Temperature（温度）会调整概率分布的平坦程度：较低温度通常更集中，较高温度通常更分散。

Pᵢ = softmax(logitᵢ / T)

候选 logits 是假设数据。实际 API 的温度范围、默认值和可用性由模型提供方决定。温度趋近零时通常采用贪心式选择，但不保证整个服务完全确定。

六、Top-p 与 Temperature 有什么区别？

Temperature 改变候选 Token 的概率分布；Top-p（核采样） 则通常按照概率从高到低排列，只保留累计概率达到阈值 p 的最小候选集合，再从中采样。

参数主要作用
Temperature调整概率分布的集中程度
Top-p限制参与采样的候选集合
Max output tokens限制最大生成长度

这些参数不会直接让模型学到新知识，也不能保证消除幻觉。很多 API 建议优先调整 Temperature 或 Top-p 中的一个，而不是同时大幅修改。

七、推理性能：TTFT、TPS 与延迟

7.2 为什么输出到一半时可能变慢？

首先要理解一个关键区别：

Prefill 通常更偏向计算密集型，而 Decode 在很多部署场景下更容易受到内存带宽限制。

这是因为在 Decode 阶段，模型通常需要逐 Token 执行前向计算，并访问模型权重和 KV Cache。

假设：

用户提问
   ↓
Prefill：处理 2,000 Tokens
   ↓
Decode：生成 1,000 Tokens

Decode 需要执行多轮生成。而且随着生成长度增加，KV Cache 也可能不断增长。

但这里有个容易误解的地方：

生成越往后，并不意味着 TPS 一定持续下降。

真实推理性能还受到批处理策略、注意力实现、硬件、服务端负载以及缓存管理方式影响。

7.3 如何计算生成速度？

假设模型在首 Token 之后，用 8 秒生成了 400 个额外 Token。

那么：

TPS = 400 / 8 = 50

即每秒生成 50 Tokens。

你可以通过下面的实验理解 TTFT 和 TPS 对用户体验的影响。

交互实验：推理延迟计算器
首 Token 等待4.9s
预计总耗时14.9s
简化估算：总耗时 ≈ TTFT + (输出 Token 数 − 1) / 后续 TPS，假设生成速度恒定。

从这个实验可以得出两个工程结论：

  • 如果用户一直看不到第一个字，应该重点排查 TTFT。
  • 如果已经开始输出，但生成非常缓慢，应该重点关注 Decode 吞吐量。

八、TypeScript：如何实现 ChatGPT 式流式聊天？

这是本篇最重要的工程实践。

假设你的技术栈是：

  • React：聊天界面。
  • Node.js：后端服务。
  • OpenAI SDK：调用大语言模型。
  • HTTP Streaming：增量传输。

8.1 整体架构

流式聊天系统架构
React Chat UI用户输入 / 实时渲染 / 停止生成
↓
Node.js API鉴权 / 组装 Messages / 流式转发

8.2 Node.js 后端示例

首先安装：

npm install openai express
npm install -D @types/express typescript tsx

创建 server.ts：

import express from "express";
import OpenAI from "openai";

const app = express();
const client = new OpenAI();

app.use(express.json());

app.post("/api/chat", async (req, res) => {
  const message = req.body?.message;

  if (typeof message !== "string" ||
      !message.trim() ||
      message.length > 10000) {
    res.status(400).json({
      error: "Invalid message"
    });
    return;
  }

  res.setHeader("Content-Type", "text/plain; charset=utf-8");
  res.setHeader("Cache-Control", "no-cache");
  res.flushHeaders();

  const controller = new AbortController();

  res.on("close", () => {
    if (!res.writableEnded) controller.abort();
  });

  try {
    const stream = await client.chat.completions.create(
      {
        model: "gpt-4.1-mini",
        messages: [
          { role: "user", content: message }
        ],
        stream: true
      },
      { signal: controller.signal }
    );

    for await (const chunk of stream) {
      if (controller.signal.aborted) break;

      const content =
        chunk.choices[0]?.delta?.content;

      if (content) res.write(content);
    }

    if (!res.writableEnded) res.end();
  } catch (error) {
    console.error(error);
    if (!res.writableEnded) res.end();
  }
});

app.listen(3000);

这个示例使用原始文本流，方便理解原理，并不是严格的 SSE 事件格式。

在生产环境中，还需要增加用户鉴权、请求限流、错误事件协议、日志和持久化等机制。

尤其需要注意：响应头已经发送后，不能再像普通 JSON API 一样随意修改 HTTP 状态码。

8.3 React 前端实现流式渲染

接下来，我们使用 Fetch API 的 ReadableStream 读取响应。

import { useRef, useState } from "react";

export function Chat() {
  const [message, setMessage] = useState("");
  const [answer, setAnswer] = useState("");
  const [loading, setLoading] = useState(false);

  const controllerRef =
    useRef<AbortController | null>(null);

  async function sendMessage() {
    if (!message.trim() || loading) return;

    const controller = new AbortController();
    controllerRef.current = controller;

    setLoading(true);
    setAnswer("");

    try {
      const response = await fetch("/api/chat", {
        method: "POST",
        headers: {
          "Content-Type": "application/json"
        },
        body: JSON.stringify({ message }),
        signal: controller.signal
      });

      if (!response.ok || !response.body) {
        throw new Error("Request failed");
      }

      const reader = response.body.getReader();
      const decoder = new TextDecoder();

      while (true) {
        const { done, value } = await reader.read();

        if (done) break;

        const text = decoder.decode(value, {
          stream: true
        });

        setAnswer(prev => prev + text);
      }

      const tail = decoder.decode();
      if (tail) setAnswer(prev => prev + tail);
    } catch (error) {
      if (!controller.signal.aborted) {
        console.error(error);
      }
    } finally {
      setLoading(false);
      controllerRef.current = null;
    }
  }

  function stopGeneration() {
    controllerRef.current?.abort();
  }

  return (
    <div>
      <textarea
        value={message}
        onChange={e => setMessage(e.target.value)}
      />

      <button onClick={sendMessage}>
        发送
      </button>

      <button onClick={stopGeneration}>
        停止生成
      </button>

      <div>{answer}</div>
    </div>
  );
}

这里最重要的代码是：

const reader = response.body.getReader();

它允许前端逐块读取响应数据。

每收到一块数据，就更新 React 状态：

setAnswer(prev => prev + text);

因此，用户可以看到文字逐步出现。

但有一个非常重要的区别：

网络 Chunk 不等于 Token。

一次网络 Chunk 可能包含多个 Token，也可能只包含一个 Token 的部分 UTF-8 字节。

这也是为什么我们使用 TextDecoder 并开启 stream: true。

九、生产级 AI 聊天机器人应该如何优化？

当用户规模增加后，除了让聊天机器人能够回答问题，还需要关注延迟、成本、并发和稳定性。

9.1 常见性能问题与优化方向

问题可能原因优化方向
首字输出慢Prefill、排队、网络缩短上下文、缓存提示词
持续生成慢Decode 吞吐量不足模型选型、推理服务优化
显存不足KV Cache、并发过高限流、GQA、缓存管理
成本过高输入输出 Token 过多摘要、缓存、模型分级
前端卡顿频繁更新 React 状态批量更新、节流渲染

9.2 为什么需要限制上下文长度？

假设一个聊天机器人有 100 轮历史消息。

如果每次请求都把所有历史消息发送给模型，就可能出现：

第 1 轮：  100 Tokens
第 2 轮：  300 Tokens
第 3 轮：  500 Tokens
...
第 100 轮：20,000 Tokens

这会增加输入 Token 成本和 Prefill 计算负担。

实际应用通常需要结合：

  • 最近消息窗口。
  • 历史对话摘要。
  • 相关记忆检索。
  • 系统提示词缓存。

这些属于应用层上下文管理，与模型内部的 KV Cache 并不是一回事。

9.3 如何衡量优化是否有效？

建议至少监控：

指标目标
TTFT P50/P95观察首字响应延迟
Decode TPS观察持续生成速度
输入 / 输出 Token分析使用量和成本
错误率识别超时与服务失败
取消率识别用户主动中止
上下文长度识别超长请求

对于生产级服务，建议分别观察 P50、P95 和 P99，而不是只看平均值。

十、本篇总结

我们把今天学习的知识串联起来：

1. Prefill处理已有输入上下文
↓
2. Decode逐步生成下一个 Token
↓
3. KV Cache缓存历史 Key / Value，减少重复计算
↓
4. Temperature / Top-p控制 Token 采样策略
↓
5. Streaming把生成内容增量传输给客户端

最重要的一句话：

模型通过 Prefill 处理已有上下文，通过 Decode 逐 Token 生成内容，通过 KV Cache 提升推理效率，而聊天应用通过 Streaming 将生成结果实时呈现给用户。

十二、学习疑问与解答

Q1：有了 KV Cache，Attention 的计算就没有成本了吗？

不是。KV Cache 省去历史 K/V 的重复计算，但新 Token 仍需与可访问的历史位置计算注意力，而且缓存需要显存。

Q2：Temperature 设为零，就一定得到完全相同的回答吗？

不一定。贪心选择降低采样随机性，但并行数值计算、服务端实现和模型版本等因素仍可能造成差异。

Q3：为什么用户已经发出的完整问题不违反 Causal Mask？

问题在生成开始前已作为输入上下文存在；因果掩码限制的是模型在某个序列位置访问未来位置，而不是禁止它阅读用户已经提供的内容。

Q4：SSE 和 Token 生成是一回事吗？

不是。Token 生成发生在模型推理层；SSE 等协议负责把服务端的增量事件传给浏览器。一次网络事件也不一定严格对应一个 Token。
