📘 第 10 篇：聊天机器人的记忆系统——短期记忆、长期记忆与语义检索

《AI 聊天机器人学习教程》｜第 10 / 40 篇

所属阶段：第二阶段 · 聊天机器人核心原理
阅读时间：约 15 分钟
技术栈：TypeScript + Node.js + Vue 3

一、为什么聊天机器人需要记忆？

假设你今天告诉 AI：

我是一名前端开发工程师，以后给我代码示例时，优先使用 TypeScript。

第二天，你打开一个新对话：

帮我实现一个防抖函数。

如果聊天机器人具有长期记忆，它就可能主动选择 TypeScript，而不需要你重复说明。

但这里有一个重要问题：

大语言模型本身并不等于记忆数据库。

聊天机器人能够记住信息，通常依赖应用层的记忆管理系统。

我们可以把记忆分成三类。

记忆类型作用存储位置
短期记忆理解当前对话Messages / 上下文
长期记忆跨会话保存偏好和事实数据库、向量索引
KV Cache加速模型推理推理服务内存或显存

需要特别注意：

KV Cache 不是长期记忆。

它主要用于避免重复计算历史 Token 的 Key 和 Value。

二、记忆系统的核心架构

一个完整的记忆系统通常包含两条独立流程。

2.1 写入记忆

纯文本
用户发送消息
     ↓
判断是否值得保存
     ↓
提取候选记忆
     ↓
验证、去重、处理冲突
     ↓
保存数据库
     ↓
更新检索索引

例如：

纯文本
用户：
以后代码示例优先使用 TypeScript。

可以提取为：

JSON
{
  "category": "preference",
  "content": "代码示例优先使用 TypeScript",
  "scope": "user"
}

但不是所有聊天内容都应该保存。

例如临时问题、过期信息、未经验证的推断，以及不必要的敏感信息，都不应该默认永久保存。

2.2 读取记忆

纯文本
用户提出新问题
     ↓
识别当前任务
     ↓
检索相关记忆
     ↓
检查权限和有效期
     ↓
根据相关性排序
     ↓
注入 Messages
     ↓
LLM 生成回答

长期记忆的关键不是保存所有内容，而是在正确的时候取出正确的信息。

三、短期记忆：Sliding Window 与 Summary

假设用户与机器人已经进行了 100 轮对话。

如果每次请求都发送全部历史消息，会出现两个问题：

  1. 输入 Token 成本越来越高。
  2. Prefill 需要处理越来越长的上下文。

因此可以使用滑动窗口。

TypeScript
const recentMessages = messages.slice(-20);

这样只保留最近 20 条消息。

但是，如果用户的重要要求出现在更早的消息中，就可能被丢弃。

另一种方式是历史摘要：

纯文本
原始历史：
用户介绍了自己的技术背景、
项目情况和代码风格偏好。

压缩摘要：
用户是前端开发工程师，
优先使用 TypeScript，
目前正在学习 AI 聊天机器人开发。

摘要能够减少 Token，但属于有损压缩。

例如，把“每月 1 号投入 800 美元”摘要为“每月投资”，就丢失了重要的日期和金额。

因此，关键事实最好保留结构化记录和原始来源。

四、长期记忆的数据结构

实际开发中，不建议只保存一段字符串。

可以使用以下 TypeScript 类型：

TypeScript
type MemoryRecord = {
  id: string;
  userId: string;

  scope: "user" | "project";

  content: string;

  category:
    | "preference"
    | "fact"
    | "task";

  sourceMessageId?: string;

  createdAt: string;
  updatedAt: string;
  expiresAt?: string;

  status:
    | "active"
    | "superseded"
    | "deleted";
};

为什么需要 status？

假设用户之前说：

代码示例优先 Python。

后来又说：

以后改成 TypeScript。

记忆系统不能让两条互相冲突的偏好同时生效。

更合理的方式是让新偏好生效，并将旧记录标记为已被替代。

五、Embedding 如何帮助检索记忆？

假设数据库保存了一条记忆：

用户喜欢使用 TypeScript 开发前端应用。

后来用户问：

我之前说过代码示例用什么语言吗？

这两句话并没有完全相同的关键词，但语义相关。

我们可以通过 Embedding 将文本转换成向量，再执行相似度检索。

典型流程：

纯文本
用户当前问题
     ↓
Embedding
     ↓
生成查询向量
     ↓
向量数据库检索
     ↓
获取相关记忆
     ↓
权限过滤与重排序
     ↓
注入当前上下文

不过，向量相似度高不代表信息一定正确。

实际系统还需要考虑记忆来源、时间有效性和用户权限。

六、TypeScript：实现一个简单记忆检索器

下面先用关键词匹配演示检索流程。

TypeScript
type Memory = {
  id: string;
  userId: string;
  projectId?: string;
  content: string;
  updatedAt: number;
  deleted?: boolean;
};

function retrieve(
  records: Memory[],
  userId: string,
  query: string,
  projectId?: string
) {
  const terms = query
    .toLowerCase()
    .split(/\s+/)
    .filter(Boolean);

  return records
    .filter(m =>
      m.userId === userId &&
      !m.deleted
    )
    .filter(m =>
      !m.projectId ||
      m.projectId === projectId
    )
    .map(m => ({
      record: m,
      score: terms.filter(t =>
        m.content.toLowerCase().includes(t)
      ).length
    }))
    .filter(x => x.score > 0)
    .sort((a, b) =>
      b.score - a.score ||
      b.record.updatedAt - a.record.updatedAt
    )
    .slice(0, 5)
    .map(x => x.record);
}

这是教学实现，并不具备真正的语义检索能力。

生产环境可以使用 PostgreSQL + pgvector 等方案。

注意：用户权限过滤应在可信数据库查询层完成，而不是先读取全部用户数据再交给模型判断。

七、长期记忆是否应该覆盖用户当前要求？

不应该。

例如，长期记忆中保存：

用户代码示例优先 TypeScript。

但用户这次明确要求：

请使用 Python 实现。

机器人就应该优先满足当前明确要求，而不是机械地坚持 TypeScript。

长期记忆应该作为辅助上下文，而不是不可修改的命令。

当然，用户当前要求也不能覆盖更高优先级的安全和权限约束。

八、如何实现记忆更新与遗忘？

一个可靠的记忆系统需要支持更新、过期和删除。

场景处理方式
用户修改偏好新记录生效，旧记录失效
临时任务完成归档或过期
用户要求删除记忆删除或失效相关记录及索引
记忆来源不可靠降低可信度或不保存

不能只在 Prompt 中写一句“忘记这件事”，就认为已经删除了数据库中的信息。

九、如何评估记忆系统？

生产环境建议关注以下指标：

指标作用
记忆召回率是否找到真正相关的记忆
错误注入率是否把不相关信息加入上下文
过期记忆命中率是否使用失效信息
跨用户数据泄漏率检查权限隔离
用户纠错成功率修改偏好后能否正确生效
Token 成本记忆注入是否过度消耗上下文

其中，跨用户数据泄漏属于高优先级安全问题。

十、本篇总结

今天需要记住五个概念。

概念核心作用
短期记忆保留最近对话
长期记忆跨会话持久化信息
Embedding支持语义检索
记忆注入将相关信息加入上下文
遗忘机制允许更新、过期和删除

最重要的一句话：聊天机器人的记忆不是模型自动记住一切，而是应用系统决定保存什么、检索什么，以及何时遗忘。

十二、学习疑问与解答

Q1：模型会因为聊天次数增加而自动训练自己吗？

普通聊天推理不会直接修改模型权重。应用可以保存和检索记忆，但这不等于重新训练模型。

Q2：是否需要保存每一句对话？

不需要。应该根据实际价值、隐私、用户意愿和保留期限决定。

Q3：记忆是否应该永远覆盖当前指令？

不应该。相关历史偏好通常应该让位于用户当前明确要求。

Q4：为什么长期记忆需要权限过滤？

因为记忆可能包含用户或项目数据。必须防止跨用户、跨租户和跨项目的数据泄漏。
