📘 第 09 篇：多轮对话与上下文管理——ChatGPT 为什么能记住我们之前聊过的内容？

第 09 / 40 篇

第二阶段：聊天机器人核心原理

阅读约 15–20 分钟

上一章，我们学习了 Prompt 和 Messages，知道聊天机器人可以通过不同角色的消息组织指令和对话。

但这里留下了一个重要的问题：

如果大语言模型本身不会因为普通聊天而持续更新参数，为什么 ChatGPT 还能记住我们前面聊过的内容？甚至在开启新对话后，有时也能记住用户的偏好？

答案涉及三个层次：

  • 模型层：Transformer 如何利用当前上下文。

  • 应用层：如何保存、裁剪和重新组织历史消息。

  • 记忆层：如何把重要信息保存下来，并在未来需要时检索。

本篇我们将从原理讲到工程实现，最终使用 TypeScript 设计一个具有多轮对话能力的 AI 聊天机器人。

一、大语言模型本身真的有记忆吗？

先看一个例子。

第一轮：

用户：我是一名前端工程师，目前正在学习 React。

第二轮：

用户：它和 Vue 有什么区别？

模型为什么可能知道「它」指 React？

因为模型能够利用当前请求中提供的历史上下文。

但如果我们只发送第二轮问题：

TypeScript
const messages = [
  {
    role: "user",
    content: "它和 Vue 有什么区别？"
  }
];

模型可能无法确定「它」指代什么。

1.1 模型参数与对话记忆不是一回事

概念

保存什么

是否跨请求持续存在

模型权重

训练中学到的模式和能力

是

当前上下文

本次推理可访问的信息

取决于请求

KV Cache

推理时的中间 K/V 状态

取决于缓存生命周期

聊天历史

用户和助手的历史消息

由应用保存

长期记忆

用户偏好、重要事实等

由记忆系统管理

所以，聊天机器人能够记住对话，不等于大语言模型的参数发生了变化。

对于常见的无状态聊天 API，每次请求都需要由应用提供相关上下文。某些 API 支持服务端保存会话状态，但本质上仍需要有状态管理机制。

二、多轮对话是如何实现的？

一个最简单的聊天机器人，可以在每次请求时，把历史消息一起发送给模型。

多轮聊天系统的基本架构

React Chat UI

发送用户消息、显示历史记录

Node.js Chat API

鉴权、读取会话、组装上下文

PostgreSQL / Redis

保存消息、会话状态和缓存

LLM API

根据传入的上下文生成回答

消息持久化

保存回答，供下一轮对话使用

这是简化的顺序示意；实际数据库读取和写入发生在后端请求处理的不同阶段。

2.1 一次多轮对话的完整流程

假设用户发起第三轮对话。

后端需要：

  1. 根据用户身份验证会话访问权限。

  2. 从数据库读取相关历史消息。

  3. 根据上下文窗口限制裁剪或摘要历史。

  4. 将 System Prompt、历史消息和当前问题组合成 Messages。

  5. 调用 LLM，并将新回答保存到数据库。

2.2 TypeScript 示例

TypeScript

type Role = "user" | "assistant";

interface ChatMessage {
  role: Role;
  content: string;
}

const history: ChatMessage[] = [
  {
    role: "user",
    content: "我正在学习 React。"
  },
  {
    role: "assistant",
    content: "React 是一个 UI 库。"
  }
];

function buildMessages(
  history: ChatMessage[],
  question: string
) {
  return [
    {
      role: "system" as const,
      content: "你是一名前端技术导师。"
    },
    ...history,
    {
      role: "user" as const,
      content: question
    }
  ];
}

const messages = buildMessages(
  history,
  "它和 Vue 有什么区别？"
);

console.log(messages);

这就是最基础的多轮对话实现方式。

不过，它会带来一个问题：

随着聊天轮数增加，历史消息会越来越长。

三、为什么不能无限发送聊天历史？

假设用户每轮产生：

  • 用户输入：100 Tokens。

  • AI 回答：400 Tokens。

那么一轮对话约为 500 Tokens。

当对话达到 100 轮时，历史消息就可能达到：

100×(100+400)=50,000 Tokens100\times(100+400)=50,000\ \text{Tokens}100×(100+400)=50,000 Tokens

如果达到 500 轮：

500×500=250,000 Tokens500\times500=250,000\ \text{Tokens}500×500=250,000 Tokens

对于上下文窗口较小的模型，这可能已经超出限制。

即使没有超限，也可能导致：

  • API 成本增加。

  • Prefill 时间增加。

  • 无关历史产生噪声。

  • 模型遗漏重要信息。

四、上下文管理的四种常见策略

为了解决历史消息越来越长的问题，聊天机器人通常需要采用不同的上下文管理策略。

4.1 全量历史（Full History）

最简单的方案：

TypeScript
const messages = [
  systemPrompt,
  ...allHistory,
  currentMessage
];

优点是实现简单、保留的信息完整。

缺点是成本和上下文占用持续增长。

4.2 滑动窗口（Sliding Window）

只保留最近 N 轮对话。

例如：

纯文本
第 1 轮：用户询问 React 第 2 轮：AI 回答 React 第 3 轮：用户询问 Vue 第 4 轮：AI 回答 Vue 第 5 轮：用户询问状态管理 第 6 轮：AI 回答状态管理

假设只保留最近两轮完整问答，那么更早的消息将不会被发送给模型。

真实应用应按照完整消息及工具调用关系裁剪，避免破坏消息结构。

4.3 历史摘要（Conversation Summarization）

滑动窗口的问题是：重要信息可能被裁剪。

例如用户在第一轮说：

我正在开发一个 React + NestJS 的企业系统。

后面聊天了 100 轮。

如果只保留最近 10 轮，这条背景就可能丢失。

历史摘要可以把较早的对话转换为简短的状态说明：

纯文本
对话摘要： 用户正在开发 React + NestJS 企业管理系统。 用户偏好 TypeScript 示例。 当前主要讨论统一鉴权和微前端架构。

后续请求可以采用：

纯文本
System Prompt + 历史摘要 + 最近几轮完整消息 + 当前用户问题

但摘要也存在信息丢失、错误归纳和过期的问题，因此需要定期更新、校验和管理。

4.4 记忆检索（Memory Retrieval）

另一种方案是将重要信息存储在外部记忆系统中。

例如：

纯文本
Memory 1：用户主要使用 TypeScript Memory 2：用户正在学习 AI 聊天机器人 Memory 3：教程需要包含交互式练习 Memory 4：GitHub 页面需要 1:1 还原

当用户说：

继续生成下一篇教程。

应用可以检索与「教程」相关的记忆，而不是发送所有历史对话。

不过，记忆的存储、更新和检索都需要独立设计，不能假设模型天然拥有无限长期记忆。

五、短期记忆与长期记忆有什么区别？

这是 AI 聊天机器人架构设计中的重要概念。

我们可以将记忆分成三个层次：

聊天机器人记忆系统

工作记忆（Working Memory）

当前请求中的 Messages、工具结果、上下文信息

会话记忆（Session Memory）

当前会话的完整消息、摘要与任务状态

长期记忆（Long-term Memory）

跨会话保存的偏好、重要事实、项目规则与历史经验

这是工程设计中的概念划分，不是所有 AI 产品都采用完全相同的记忆架构。

5.1 工作记忆

工作记忆就是模型当前能够访问的信息。

例如：

TypeScript
const messages = [
  {
    role: "system",
    content: "你是前端技术导师。"
  },
  {
    role: "user",
    content: "React 和 Vue 有什么区别？"
  }
];

这段内容只说明当前请求中提供了什么。

工作记忆并不等于永久存储。

5.2 会话记忆

会话记忆由应用负责维护。

例如数据库中保存：

纯文本
Conversation ID: chat_001 Message 1: 用户询问 React Message 2: AI 介绍 React Message 3: 用户询问 Vue Message 4: AI 比较 React 和 Vue

当用户刷新页面后，前端可以根据 Conversation ID 重新读取历史。

这里要区分两件事：

  • 恢复聊天界面：从数据库读取消息并展示。

  • 让模型利用历史：把相关消息重新提供给模型，或使用支持服务端会话状态的 API。

两者不是同一回事。

5.3 长期记忆

长期记忆通常保存跨会话仍然有用的信息。

例如：

JSON
{
  "userId": "user_001",
  "memories": [
    {
      "type": "preference",
      "content": "优先使用 TypeScript 示例"
    },
    {
      "type": "project_rule",
      "content": "教程同步 GitHub 必须 1:1 还原"
    }
  ]
}

以后用户开启新的对话，应用可以检索这些信息并注入上下文。

但长期记忆也不能无限保存所有内容。

实际系统需要考虑记忆的相关性、时效性、准确性、用户控制权和隐私保护。

五、短期记忆与长期记忆有什么区别？

在聊天机器人系统中，通常可以将记忆分为两类。

5.1 短期记忆（Short-term Memory）

短期记忆主要服务于当前会话。

例如：

纯文本
用户：我正在学习 React。 AI：好的，我们从基础开始。 用户：它和 Vue 有什么区别？

第二轮中的「它」需要依赖第一轮的信息。

因此，应用需要保留相关消息。

短期记忆通常包括：

  • 最近几轮对话。

  • 当前任务状态。

  • 临时变量与工具结果。

  • 当前会话的上下文摘要。

这些内容通常与某个 conversationId 关联。

5.2 长期记忆（Long-term Memory）

长期记忆则用于保存跨会话仍然有价值的信息。

例如：

纯文本
用户偏好： - 主要使用 TypeScript - 喜欢中文技术教程 - 每篇教程需要交互实验 - GitHub 必须尽量 1:1 还原

当用户开启新对话时，应用可以在获得适当授权后检索这些信息，并作为上下文提供给模型。

这里有一个重要区别：

长期记忆不是把全部聊天记录永久放进 Prompt，而是在需要时取出相关信息。

六、长期记忆如何存储与检索？

假设我们正在开发一个 AI 学习助手。

用户曾经说过：

应用可以将其整理成结构化记忆。

6.3 记忆一定需要向量数据库吗？

不一定。

七、TypeScript 实现多轮对话管理器

现在进入工程实践。

我们先实现一个不依赖框架的简单对话管理器，支持：

  • 保存聊天消息。

  • 读取历史消息。

  • 通过 Token 预算裁剪。

  • 组合 System Prompt 和当前问题。

7.1 定义消息类型

TypeScript

type ChatRole = "user" | "assistant";

interface ChatMessage {
  id: string;
  role: ChatRole;
  content: string;
  createdAt: number;
}

interface Conversation {
  id: string;
  userId: string;
  messages: ChatMessage[];
}

7.2 实现 ConversationManager

TypeScript

class ConversationManager {
  private conversations = new Map<
    string,
    Conversation
  >();

  create(
    conversationId: string,
    userId: string
  ) {
    const conversation: Conversation = {
      id: conversationId,
      userId,
      messages: []
    };

    this.conversations.set(
      conversationId,
      conversation
    );

    return conversation;
  }

  addMessage(
    conversationId: string,
    message: ChatMessage
  ) {
    const conversation =
      this.conversations.get(conversationId);

    if (!conversation) {
      throw new Error("Conversation not found");
    }

    conversation.messages.push(message);
  }

  getHistory(
    conversationId: string,
    userId: string
  ) {
    const conversation =
      this.conversations.get(conversationId);

    if (!conversation ||
        conversation.userId !== userId) {
      throw new Error("Conversation not found");
    }

    return [...conversation.messages];
  }
}

这段代码用于说明基本的数据结构。

生产环境不能依赖进程内 Map 保存全部会话，因为服务重启会丢失数据，多实例之间也无法共享状态。

实际项目应将会话和消息持久化到数据库。

另外，写入消息时也需要校验用户是否有权访问对应会话。

7.3 根据 Token 预算裁剪消息

我们可以设计一个通用函数。

TypeScript

interface Message {
  role: "user" | "assistant";
  content: string;
}

function trimHistory(
  history: Message[],
  maxTokens: number,
  countTokens: (text: string) => number
): Message[] {
  const result: Message[] = [];
  let usedTokens = 0;

  for (let i = history.length - 1; i >= 0; i--) {
    const message = history[i];
    const tokens = countTokens(message.content);

    if (usedTokens + tokens > maxTokens) {
      break;
    }

    result.unshift(message);
    usedTokens += tokens;
  }

  return result;
}

这里的 countTokens 需要使用与目标模型兼容的 Tokenizer 或计数接口实现。

还需要注意，这个简化函数仅统计文本内容，没有计算消息元数据和工具调用开销。

对于带工具调用的会话，还必须保证裁剪后的消息结构合法。

8.1 数据库应该如何设计？

一个基础聊天系统至少可以设计两张表。

SQL

CREATE TABLE conversations (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL,
  title TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE messages (
  id UUID PRIMARY KEY,
  conversation_id UUID NOT NULL
    REFERENCES conversations(id),
  role VARCHAR(20) NOT NULL,
  content TEXT NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_messages_conversation
ON messages(conversation_id, created_at);

这只是基础版本。

生产环境还需要考虑消息状态、工具调用记录、消息顺序、幂等性、删除策略和多租户隔离。

8.2 为什么要使用 Redis？

Redis 可以用于：

  • 缓存最近聊天历史。

  • 保存临时任务状态。

  • 请求限流。

  • 分布式锁或其他协调机制。

但 Redis 不一定要承担全部持久化职责。

对于需要长期保存的聊天记录，通常应使用可靠的持久化存储。

九、生产级上下文管理与性能优化

一个生产级聊天机器人不能只追求「记住得多」，还需要平衡准确性、成本、延迟和隐私。

9.1 推荐的上下文组织方式

纯文本
System Prompt + 用户长期记忆（经过相关性筛选） + 历史对话摘要 + 最近几轮完整消息 + 当前用户问题

但这不是固定公式。

不同任务需要不同策略。例如代码调试更依赖最近的错误日志，而长期学习助手可能更依赖用户目标和学习进度。

9.2 需要重点监控的指标

指标

作用

Input Tokens

衡量上下文成本

TTFT

衡量首字响应延迟

衡量记忆召回情况

Retrieval Relevance

评估检索相关性

观察历史裁剪频率

评估回答正确性

记忆命中率越高，不一定代表回答越好。

错误或过期记忆被频繁召回，反而可能降低回答质量。

9.3 长期记忆的安全与隐私

长期记忆还需要考虑：

  • 用户是否同意保存。

  • 用户能否查看和更正记忆。

  • 用户能否删除记忆。

  • 敏感信息是否需要禁止存储。

  • 记忆是否设置有效期。

  • 多用户之间是否存在数据隔离。

长期记忆是一项产品能力，同时也是数据治理责任。

学习疑问与解答（本地补充） ​

Q1：恢复聊天界面，为什么不等于让模型知道历史？ ​

恢复 UI 是从数据库读取消息并渲染 React；让模型利用历史，则需要在推理请求中提供相关消息，或使用支持服务端会话状态的 API。两条流程的服务对象不同。

Q2：短期记忆与长期记忆分别适合什么数据库？ ​

会话历史可存 PostgreSQL、MySQL、MongoDB 或 SQLite；Redis 可用于热点会话缓存。长期结构化记忆可存 PostgreSQL，语义检索可用 pgvector、Qdrant、Milvus 等。

Q3：PostgreSQL 是向量数据库吗？ ​

PostgreSQL 本质是关系型数据库。安装 pgvector 扩展后，可以在同一数据库中存储 Embedding 向量并执行相似度检索。初期 AI 聊天机器人推荐 PostgreSQL + pgvector；确有性能需求再加 Redis。

Q4：为什么长期记忆不应该直接等于全部聊天记录？ ​

聊天历史可能包含无关、过期或敏感内容。长期记忆应按价值、授权、有效期与相关性筛选，并提供查看、更正和删除机制。

Q5：KV Cache 是不是长期记忆？ ​

不是。KV Cache 是模型推理时复用的 Key/Value 中间状态，不是面向用户偏好和项目事实的持久化记忆库。
