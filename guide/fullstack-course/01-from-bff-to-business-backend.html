第 01 篇：从 BFF 思维走向业务后端 ​

全栈进阶系列 · 01 / 12 · 建议阅读 25 分钟，实践 2～3 小时

适合已经开发过 Node BFF、使用过 Java Spring Boot 的前端开发者。本文不重复路由和 Controller 入门，重点训练业务设计与正确性判断。

你可能已经写过这样的链路：前端调用 Node BFF，BFF 聚合几个接口，Spring Boot 查询数据库并返回结果。页面能跑通，接口也能交付，但当需求变成“只有指定团队的人可以接单，两个人同时点击只能成功一个，接单后必须留下记录”时，开发的难点就变了。

你需要开始对业务规则在不同入口、并发请求和失败情况下是否成立负责。这是本系列的学习主线。

本文用一个团队工单系统贯穿讲解。读完后，你应当能划分前端、BFF、业务服务和数据库的责任，定义一条接单接口，并解释为什么事务不能自动解决并发问题。

1. 先把业务场景说清楚 ​

团队成员可以提交工单，处理人接单后推进处理，提单人确认后关闭。第一篇只研究“接单”。

假设工单 123 属于团队 10，当前状态为待接单。用户小林和小周都具有该团队的接单权限，他们可能同时点击按钮。

我们约定以下规则：

  1. 用户必须已登录，且是工单所属团队中具有接单权限的有效成员。
  2. 只有待接单工单可以接单。
  3. 接单成功后，状态变为处理中，当前用户成为处理人。
  4. 两个人竞争同一张待接单工单时，只能有一人成功。
  5. 接单结果和操作记录必须一起保存成功，或者一起回滚。
  6. 通知允许稍后送达；通知服务故障不应把已完成的接单变更撤销。

这些约定是后续代码和测试的依据。没有明确规则，“接口成功”就只能代表代码执行到了返回语句。

2. BFF 和业务后端的边界在哪里 ​

本系列采用以下结构：

text
前端页面
   │ 用户交互、加载状态、错误反馈
   ▼
Node BFF
   │ 页面数据聚合、字段适配、下游调用控制
   ▼
Spring Boot 业务服务
   │ 身份验证、权限检查、业务规则、事务
   ▼
关系型数据库
     持久化、约束、并发控制
前端页面
   │ 用户交互、加载状态、错误反馈
   ▼
Node BFF
   │ 页面数据聚合、字段适配、下游调用控制
   ▼
Spring Boot 业务服务
   │ 身份验证、权限检查、业务规则、事务
   ▼
关系型数据库
     持久化、约束、并发控制

BFF 是面向特定前端的数据服务层。例如工单详情页需要工单、处理人摘要和权限提示，BFF 可以把多个下游响应整理为页面需要的结构。

业务服务负责独立于页面存在的规则。即使明天增加移动端、开放 API 或后台批处理，非法用户也不能接单，已关闭工单也不能重新被接走。

需求主要归属判断理由
状态显示为中文、时间显示为相对时间前端或 BFF服务展示体验
聚合工单与人员摘要BFF服务页面的数据组织
当前用户是否有接单权限业务服务对所有调用入口生效
同一工单只允许一人接单成功业务服务与数据库涉及竞争下的数据变更
接单变更和操作记录一起提交业务服务中的数据库事务属于同一原子操作
通知失败后的重试后台任务需要独立恢复

判断规则放在哪里，可以问：如果完全绕过这个页面，这条规则是否仍必须成立？ 如果答案是“必须”，就不能只在页面或 BFF 中实现。

这里的划分来自职责，不是来自语言。Node.js 也可以承载业务服务；本系列使用 Spring Boot，是为了复用你已有经验。某个页面直接调用业务服务就足够时，也不必为了架构完整而额外增加 BFF。

2.1 隐藏按钮不等于完成权限控制 ​

前端可以根据 allowedActions 隐藏接单按钮，但用户仍能手动构造 HTTP 请求。后端必须重新检查权限和当前状态。

即使页面刚拿到 canClaim: true，下一秒也可能被别人接走。这种提示只表示查询时刻的判断，不构成接单承诺。

2.2 不要直接信任浏览器传来的身份 ​

下面的请求体有问题：

json
{
  "userId": "456",
  "teamId": "10",
  "role": "ADMIN"
}
{
  "userId": "456",
  "teamId": "10",
  "role": "ADMIN"
}

如果后端直接采用这些字段，用户就能冒充别人。当前操作者应来自经过验证的认证上下文，角色和成员关系应由服务端确认。

如果 BFF 向下游转发身份，可以使用业务服务能够验证的访问令牌，或者有明确认证机制的内部身份上下文。业务服务不能仅凭一个可被外部伪造的 X-User-Id 请求头信任调用者。网关也应移除外部传入的内部身份头。

一个通用更新接口可能接受：

http

Content-Type: application/json

Content-Type: application/json
json
{
  "status": "PROCESSING",

这表达了目标数据，却没有区分接单、管理员指派和重新打开。它们可能具有不同权限、前置条件和操作记录。

对于本项目，我们为业务动作定义专门接口：

http
POST /api/tickets/123/claim
POST /api/tickets/123/claim

请求体为空，当前用户由认证上下文确定。管理员指派给他人应当使用独立操作，并执行相应权限检查。标题、描述等普通编辑仍可使用 PATCH。

3.1 接口契约 ​

成功响应使用 200 OK，返回更新后的资源摘要：

json
{
  "id": "123",
  "status": "PROCESSING",
  "assigneeId": "456",
  "version": 1
}
{
  "id": "123",
  "status": "PROCESSING",
  "assigneeId": "456",
  "version": 1
}

示例将 ID 表达为字符串，避免数据库大整数超出 JavaScript 安全整数范围。具体项目也可以使用 UUID，关键是全链路统一。

失败响应统一为：

json
{
  "error": {
    "code": "TICKET_STATE_CONFLICT",
    "message": "工单状态已变化，请刷新后重试"
  },
  "requestId": "req-example-001"
}
{
  "error": {
    "code": "TICKET_STATE_CONFLICT",
    "message": "工单状态已变化，请刷新后重试"
  },
  "requestId": "req-example-001"

未登录或凭据无效401UNAUTHENTICATED

前端根据错误码决定跳转登录、刷新工单或展示失败提示。BFF 应保留有意义的业务错误，避免把所有下游错误都转换成 200 或“服务异常”。原始数据库错误、堆栈等内部信息不能直接返回浏览器。

状态表可以用于需求评审、后端规则、页面动作展示和测试设计。不需要第一天就引入状态机框架；先让规则明确且集中。

5. 为什么加了事务，还是可能重复接单 ​

常见实现如下。以下 Java 是展示控制流程的伪代码，省略了类、依赖注入和异常定义，不是可直接运行的完整项目。

java
@Transactional
public void claim(long ticketId, Actor actor) {
    Ticket ticket = repository.findVisible(ticketId, actor);
    permissionService.requireClaimPermission(actor, ticket);

    if (ticket.status() != OPEN) {
        throw new TicketStateConflictException();
    }

    repository.assign(ticketId, actor.userId(), PROCESSING);
    operationLog.append(ticketId, actor.userId(), "CLAIM");
}
@Transactional
public void claim(long ticketId, Actor actor) {
    Ticket ticket = repository.findVisible(ticketId, actor);
    permissionService.requireClaimPermission(actor, ticket);

    if (ticket.status() != OPEN) {
        throw new TicketStateConflictException();
    }

    repository.assign(ticketId, actor.userId(), PROCESSING);
    operationLog.append(ticketId, actor.userId(), "CLAIM");
}

这里的问题是查询与修改之间存在时间窗口：

时间小林的请求小周的请求
T1查询到 OPEN
T2查询到 OPEN
T3更新处理人为小林并提交
T4更新处理人为小周并提交

两个请求都可能返回成功，后一次更新覆盖前一次。具体行为取决于 SQL、隔离级别和 ORM 是否配置版本检查，但单独出现 @Transactional 并不能证明不会发生这个问题。

事务解决一组操作如何一起提交或回滚；并发控制还需要定义竞争时允许谁修改。

5.1 把前置条件放进更新语句 ​

对于“只能从待接单变为处理中”，可以执行条件更新：

sql
UPDATE tickets
SET assignee_id = :userId,
    status = 'PROCESSING',
    version = version + 1
WHERE id = :ticketId
  AND team_id = :teamId
  AND status = 'OPEN'
  AND assignee_id IS NULL;
UPDATE tickets
SET assignee_id = :userId,
    status = 'PROCESSING',
    version = version + 1
WHERE id = :ticketId
  AND team_id = :teamId
  AND status = 'OPEN'
  AND assignee_id IS NULL;

冒号参数表示框架绑定的命名参数，不是字符串拼接。这段 SQL 假定表中已有相关字段，使用支持事务的数据库引擎；本篇不展开建表和 Repository 配置。

数据库通过其锁与条件更新机制协调竞争。应用检查受影响行数：

  • 1：当前请求完成了状态变更。
  • 0：当前请求未满足更新条件。

两个请求竞争同一行时，常见事务配置下其中一个更新成功，另一个在等待后发现条件不满足；某些配置或冲突场景也可能返回锁超时、死锁或序列化失败，需要后续明确处理。无论哪种情况，都不应把两个请求都当成接单成功。

单独增加 version 不等于完成乐观锁。若希望检查用户基于哪个版本修改，需要在 WHERE 中匹配预期版本，或者使用 ORM 提供的版本机制。本例依靠状态条件阻止重复接单。

5.2 受影响行数为零，不一定都是状态冲突 ​

也可能是工单不存在、团队不匹配，或数据违反了当前约定。本项目先查询可见资源并检查权限，再执行条件更新，因此可以把竞争导致的更新失败按状态冲突处理，同时通过服务端日志排查异常。

查询必须按当前用户可访问范围进行；teamId 不能直接取自未经验证的请求参数。如果权限可能在操作期间被撤销，还需定义撤销何时生效，并在后续权限篇选择相应的一致性策略。本篇假定请求执行期间成员权限保持不变。

6. 接单与操作记录必须共享一个事务 ​

接单结果是业务数据，操作记录是可审计的业务历史。如果工单变成处理中，但操作记录写入失败，两者就不一致了。

text
开始数据库事务
  → 查询可见工单，检查权限
  → 执行条件更新，检查受影响行数
  → 写入接单操作记录
  → 提交

任一步失败 → 回滚
开始数据库事务
  → 查询可见工单，检查权限
  → 执行条件更新，检查受影响行数
  → 写入接单操作记录
  → 提交

任一步失败 → 回滚

在 Spring 中需要核对以下条件：

  • 事务方法通过 Spring 事务代理调用；默认代理模式下，同一个对象内部的自调用不会触发新方法上的事务拦截。
  • 更新和操作记录使用同一事务管理器下的同一数据库事务，没有被独立事务传播配置拆开。
  • 错误需要向事务边界传播；不要捕获后悄悄返回成功。
  • 按默认声明式规则，RuntimeException 和 Error 会触发回滚；受检异常是否回滚需要显式配置，项目也可能修改默认策略。

这些是 @Transactional 是否真正实现预期的条件。详细规则见 Spring 官方事务注解文档 与 回滚规则文档。

7. 通知为什么不能直接混进数据库事务 ​

考虑下面的顺序：

text
更新工单 → 写操作记录 → 调用通知服务 → 提交数据库事务
更新工单 → 写操作记录 → 调用通知服务 → 提交数据库事务

如果通知成功后数据库提交失败，用户会收到一条没有对应业务事实的通知。如果通知服务很慢，数据库事务还会持有资源等待外部响应。

把通知移到提交后直接发送，也有缺口：数据库已经提交，但进程在发送前崩溃，通知就可能永久丢失。

后续课程会实现事务型 Outbox：

text
同一个数据库事务
  ├─ 更新工单
  ├─ 写操作记录
  └─ 写待发送事件
          ↓ 提交后
后台任务读取事件 → 发送通知 → 记录结果
                       ↓ 失败
                     延迟重试
同一个数据库事务
  ├─ 更新工单
  ├─ 写操作记录
  └─ 写待发送事件
          ↓ 提交后
后台任务读取事件 → 发送通知 → 记录结果
                       ↓ 失败
                     延迟重试

事件记录与业务结果一起提交，后台任务负责恢复发送。发送后、标记成功前仍可能崩溃，所以接收端需要处理重复，不能声称天然实现“恰好一次”。

第一篇先把它作为设计边界：接单接口成功表示接单及必要记录已提交，不代表通知已经送达。完整事件投递实现留到第 09 篇。

8. 前端与 BFF 如何配合这条链路 ​

前端可以在提交期间禁用按钮，并在成功后刷新工单；遇到 409 时提示状态变化，重新查询。禁用按钮减少误操作，但不能替代服务端并发控制。

BFF 则负责保留身份验证链路、传递可追踪的请求标识、设置明确的下游超时，并转换页面所需的数据结构。不要在 BFF 中复制完整状态流转逻辑，否则多个入口迟早会出现规则差异。

还有一个容易遗漏的情况：后端已经接单成功，但响应在网络中丢失。此时前端看到超时，却不能据此判断业务失败。

text
数据库提交成功 → 响应丢失 → 前端超时
数据库提交成功 → 响应丢失 → 前端超时

本课采取保守交互：显示“操作结果暂未确认”，重新查询工单。条件更新能避免第二次重复接单，但不等于能把同一操作的成功响应重新返回。可靠重试和请求幂等键将在第 05、08 篇继续展开。涉及写操作的重试，不能只套用统一重试配置。

9. 实践：提交一份可以评审的接单方案 ​

本篇是设计与局部实现课，不提供完整工程脚手架。你可以在熟悉的 Spring Boot 项目中完成以下练习；使用模拟身份时只允许本地开发配置，不能把测试身份机制作为正式认证上线。

9.1 交付物 ​

  1. 一张调用链路图，标出身份从哪里获得、在哪里检查权限。
  2. 一份接口契约，覆盖成功、未登录、无权限、不可见和状态冲突。
  3. 一份状态流转表，明确接单前置条件。
  4. 一段数据库条件更新，以及处理受影响行数的业务代码。
  5. 一份说明：哪些内容共享事务，哪些内容异步处理，为什么。

9.2 验收场景 ​

场景预期结果
有权限成员接单状态改变、处理人正确、生成一条接单记录
未登录请求401，无数据变更
其他团队成员访问按本项目约定返回 404，无数据变更
可见但无接单权限403，无数据变更
对已解决工单接单409，无数据变更
两名成员同时接同一工单只有一人成功，只有一条成功接单记录
操作记录插入失败接单更新回滚
请求体或请求头伪造用户身份无法冒充他人，拒绝或忽略非法字段
通知服务不可用接单结果不依赖即时送达；后续由可靠流程恢复

并发测试需要两个独立连接或事务，并用同步屏障尽量让它们同时尝试修改同一张工单。测试结束后检查成功次数、最终处理人和记录数量。不要只串行发送两次请求，那主要验证状态限制，不能充分验证竞争行为。

回滚测试应在数据库更新之后，主动让操作记录写入失败，再通过独立查询确认工单仍是待接单。只模拟 Repository 返回值，无法证明真实事务能够回滚。

10. 自测与学习疑问 ​

自测 1：前端隐藏了接单按钮，后端还需要检查权限吗？ ​

A. 不需要，用户看不到按钮。
B. 需要，客户端可绕过页面直接请求。
C. 只要 BFF 检查过，业务服务就永远不用检查。

查看答案与解析

答案：B。权限属于业务约束，必须在受信任的服务端边界成立。BFF 的页面提示和预检查不能替代业务服务的授权规则。

自测 2：为什么事务里的“先查后改”仍可能覆盖别人的接单？ ​

A. 事务只能运行一条 SQL。
B. 事务不支持查询。
C. 两个事务可能先后读到相同旧状态，修改时没有验证状态仍然成立。

查看答案与解析

答案：C。需要根据具体场景加入条件更新、版本检查或锁等并发控制。事务本身不代表所有业务请求串行执行。

自测 3：接口超时是否代表接单失败？ ​

A. 是，没收到响应就没有提交。
B. 否，服务端可能已经提交，只是响应丢失。
C. 是，再自动重试三次就能解决所有问题。

查看答案与解析

答案：B。需要查询结果或使用明确的幂等协议恢复判断，不能把网络状态直接当成业务状态。

疑问：是不是必须开始学习微服务和领域驱动设计？ ​

先把一个模块的边界、状态、权限和事务讲清楚就有很大价值。本项目从按模块组织的单体应用开始；当部署、团队协作或容量需求明确时，再讨论服务拆分。

疑问：BFF 能不能写数据库？ ​

可以，架构取决于职责。若一个 Node 服务拥有业务数据并承担事务与业务规则，它就在承担业务后端责任。本文避免让 Node BFF 和 Java 服务同时各自修改同一套工单数据，是为了保持规则与写入入口清晰。

疑问：本篇讲了很多后续内容，当前到底要掌握什么？ ​

能解释一次接单请求的完整职责分配；能指出“先查后改”的竞争窗口；能说明接单与操作记录为什么共享事务、通知为什么需要独立恢复。Outbox、幂等与完整认证实现只要求知道问题，后续逐篇实现。

11. 本篇回顾与下一篇 ​

业务后端需要让规则在不同入口、竞争和故障下持续成立。用本篇的接单场景检验自己的设计：身份可信，权限由服务端检查，状态条件参与写入，必要记录和业务变更一起提交，外部通知拥有恢复机制。
